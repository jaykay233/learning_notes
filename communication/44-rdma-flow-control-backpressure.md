## 为什么现在讲这个

[33 章](./33-rdma-six-layer-spine.md) 的 L2 表里有一句结论：**SEND 有天然背压，WRITE 没有**。
[43 章](./43-rdma-l2-remaining-semantics.md) 又从 UD 的角度说了一遍"无连接状态"。
但这句话一直被当成定性描述，没人问过：

> WRITE 没有背压，**具体会发生什么**？

答案不是"慢一点"。答案是：**发送端收到 `IBV_WC_SUCCESS`，而接收端的数据被静默覆盖。**

这是一个正确性 bug，不是性能问题。而且它无法通过调大缓冲"解决"——
因为 [33 章](./33-rdma-six-layer-spine.md) 的固定成本模型和这里的缓冲需求会一起指向同一个结论：

```text
在 400G 上，吸收 1 ms 的停顿需要 47.7 MiB 缓冲/连接
1000 条连接就是 47 GiB
```

所以"加大缓冲"在高速网络上不是选项。你必须选：**限速，或者接受覆盖**。

这一章把这件事算出来，并给出四层流控的完整分工（Q23 的答案就在最后那张图里）。

## 心智模型：三层"看起来像流控"的东西，保护的完全不是一回事

初学者最容易犯的错，是把链路 credit、PFC、DCQCN、应用 credit 当成"同一个东西的不同实现"。
它们保护的**对象**根本不同：

```text
第 1 层 链路 credit   保护「下一跳的接收缓冲」  逐跳  纳秒  计数
第 2 层 PFC           保护「入口缓冲」          逐跳  微秒  信号
第 3 层 DCQCN/ECN     保护「网络平均队列」      端到端 毫秒  速率
第 4 层 应用 credit   保护「接收端应用缓冲」    端到端 业务  语义
```

前两层保网络，后两层保端点。**关键：前三层都不知道你的应用有没有空读数据。**

```text
交换机不知道你的线程在睡觉
网卡不知道你的 slot ring 满了没
DCQCN 不知道你上一批请求还没处理完
```

所以**应用层 credit 不可省略**。这不是"再加一层保险"，而是唯一能理解"消费者忙"的机制。

### 为什么 SEND 能天然拥有第 4 层

```text
SEND 的「写到哪里」由接收端投 recv WR 时决定
  -> 接收端只有在真正有空闲缓冲时才投 WR
  -> WR 池深度 = 并发上限 = 天然的 application credit
  -> WR 用光 -> 发送端收到 RNR（一个诚实、可见的信号）

WRITE 的「写到哪里」由发送端拿到的 rkey 决定
  -> 接收端从未对「这一笔」表过态
  -> 网卡照着 rkey 写，写成功就回 SUCCESS
  -> 没有信号，没有边界检查，没有背压
```

**这是同一个环，SEND 永远安全、WRITE 永远不安全的原因。**
不是实现差异，是"谁决定目标地址"这个语义差异的必然后果。

## 账本一：停顿一下，覆盖多少

脚本 [`44_flow_control_backpressure.py`](./44_flow_control_backpressure.py)：
生产恒为线速（WRITE 无法感知对端），消费在 100 µs 处停顿 N µs，
停顿结束后以 2.5× 线速追赶排空。

```bash
cd ~/Downloads/learning_notes
python3 communication/44_flow_control_backpressure.py
```

```text
    停顿 us       停顿期间写入        环深256       环深1024       环深4096      环深16384
       10          122            0            0            0            0
      100         1220          977          209            0            0
     1000        12207        11963        11195         8123            0
    10000       122070       121827       121059       117987       105699
```

三条从表里直接读出来的事实：

1. **覆盖数是"停顿期间写入量 − 环深"的量级**。`stall=1000`（写入 12207）时，
   环深 1024 覆盖 11195 ≈ `12207 - 1024 + 12`。
2. **只有环深 ≥ 停顿期间写入量时才归零**。`stall=100` 的 1220 条，环深 4096 就够；
   `stall=10000` 的 122070 条，16384 仍然覆盖 105699。
3. **10 µs 的停顿完全无感**（122 条 < 最小环深）。这就是为什么单机测试永远发现不了——
   测试里的消费端从不真的停顿。

### 为什么"偶发数据错乱"最难查

```text
发送端：IBV_WC_SUCCESS         <- 网卡说：我写成功了
接收端：读到半新半旧的数据     <- 应用说：这不是我发的
网卡计数器：全部正常
链路：零丢包
```

因为 WQE 确实执行成功了。**没有"错误"可言，只有"结果不对"。**
这类故障的排查路径和 [37 章](./37-rdma-gpudirect-degradation.md) GPUDirect
退化、[41 章](./41-rdma-kubernetes-multitenancy.md) GID 选错是同一类：
**没有错误，只有现象**，必须从"语义"而不是"计数器"入手。

## 账本二：缓冲要多大（答案让人不舒服）

```text
        停顿        所需条数         所需容量               等价于
     10 us         122         0.5M    400G x 0.01 ms
    100 us        1220         4.8M    400G x 0.10 ms
      1 ms       12207        47.7M    400G x 1.00 ms
     10 ms      122070       476.8M   400G x 10.00 ms
```

**1 ms 停顿 @ 400G 需要 47.7 MiB 缓冲。**

这个数字的来源很朴素：400 Gbps = 50 B/ns，1 ms 就是 50 MB。缓冲要装下"停顿期间仍在到达的数据"，
所以它只取决于线速和停顿长度。

乘以连接数就更荒谬：

```text
1000 条连接 x 47.7 MiB = 47 GiB  <- 只为了扛 1 ms 抖动
```

所以高速网络上只有两条路：

```text
路 A：限速（credit）
  发送端不许超过"接收端已准备好"的量
  缓冲需求 = 环深（MB 级），不是抖动量（GB 级）

路 B：让发送端自己慢下来（DCQCN）
  靠 ECN 反馈降速，在拥塞形成前收敛
  但它只保护网络，不保护你的应用缓冲 —— 仍需路 A
```

这就是 [35 章](./35-rdma-congestion-control-loop.md) 那句话的精确含义：
**PFC/DCQCN 保护的是网络，不是你的 ring buffer。**

## 账本三：用 credit 替代缓冲，代价是什么

```text
    环深      写入条数      被覆盖     阻塞 us    有效 msg/us       缓冲容量
    64     48855        0       998         12.2       0.2M
   256     49047        0       983         12.3       1.0M
  1024     49815        0       920         12.5       4.0M
  4096     52887        0       668         13.2      16.0M
```

（停顿 1000 µs，credit 归还延迟 = RTT 3 µs）

**覆盖全部为 0。** 这是 credit 的全部意义：它解决正确性，不解决吞吐。

环深的作用是"能偷吞多少突发"：

```text
64 条（0.2 MiB）  -> 阻塞 ~998 us（几乎整个停顿期都在等）
4096 条（16 MiB） -> 阻塞 ~668 us（先吃掉 16 MiB 突发，再等剩下的）
```

而**欠账最终都要还**：停顿 1000 µs 造成的生产缺口，只能靠之后的追赶补回来。
所以最后那句最重要：

> **credit 不能让你超过消费者的处理能力。**

它把"覆盖数据"换成"发送端等待"——**用一个诚实的失败，换掉一个静默的错误。**
这个交换在任何生产系统里都值得做。

## 账本四：四层流控的分工（Q23 的答案）

```text
┌──────────────────────────────────────────────────────────────┐
│ 第 4 层  应用 credit（semantic）                             │
│   保护：接收端应用缓冲不溢出                                  │
│   机制：recv WR 计数 / 显式 credit 消息                        │
│   唯一能理解「消费者忙」的层 —— 前三层都不懂业务语义           │
├──────────────────────────────────────────────────────────────┤
│ 第 3 层  DCQCN / ECN（端到端速率）                            │
│   保护：网络平均队列，避免持续拥塞                             │
│   机制：交换机打 ECN -> CNP -> 发送端降速、加性恢复            │
│   时间尺度：毫秒；不保证零丢包（35 章）                        │
├──────────────────────────────────────────────────────────────┤
│ 第 2 层  PFC（逐跳暂停）                                     │
│   保护：交换机/网卡入口缓冲不溢出                              │
│   机制：802.1Qbb pause frame，按优先级                         │
│   时间尺度：微秒；能保证零丢包，但会反压（35 章）              │
├──────────────────────────────────────────────────────────────┤
│ 第 1 层  链路 credit（硬件）                                  │
│   保护：下一跳的接收缓冲（IB 原生）                            │
│   机制：每 VL 一个信用计数器，收一个包还一个                    │
│   时间尺度：纳秒；逐跳，端到端不感知                           │
└──────────────────────────────────────────────────────────────┘
```

### IB credit 与 PFC 的本质区别

这是 Q23 被追问最多的地方。两者都是逐跳、都能做到不丢包，但机制完全不同：

| | IB 链路 credit | PFC |
| --- | --- | --- |
| 触发方式 | **收下才还信用**（计数） | **快满了才喊停**（信号） |
| 发送端是否知道容量 | 知道（信用数就是剩余容量） | 不知道（只能靠 pause frame） |
| 是否需要 headroom | 不需要（永不超发） | **必须**（信号有传播延迟） |
| 时间尺度 | 纳秒（硬件流水线内） | 微秒（帧生成 + 传播 + 响应） |
| 失效模式 | 信用泄漏 → 永久停发 | PFC storm / 死锁（[35 章](./35-rdma-congestion-control-loop.md)） |
| 部署范围 | IB 原生 | RoCE 必需（因为底层以太网会丢） |

一句话概括：

> **credit 是"精确的许可"，PFC 是"迟到的叫停"。**
> 前者永远不会超发，所以不用留余量；后者必须按"信号飞一个来回的时间里还能进来多少"预留 headroom
> （[35 章](./35-rdma-congestion-control-loop.md) 算过：400G / 2 µs 延迟下每端口每优先级约 203 KB）。

这也解释了为什么 RoCE 需要 PFC 而不是直接用 credit：
以太网的 PAUSE/优先级暂停是"事后"机制，而 IB 从协议层就内建了信用计数。

## 账本五：SEND 与 WRITE 的对照表

```text
                   SEND                              WRITE
接收端参与    必须预投 recv WR                    完全不参与
天然背压      有：WR 用光就 RNR                   无：写到哪算哪
环满时        发送端阻塞或 RNR                    静默覆盖
应用看到      RNR_RETRY_EXC_ERR                   IBV_WC_SUCCESS
谁保护缓冲    网卡 + 应用                         只有应用自己
适合          请求/响应、需要边界                 大块单向写、已知地址
```

**"环满时"这一行是 Q53 的全部答案。** 其余各行都是它的推论。

## 设计建议（Q49 的落地部分）

```text
请求路径（小消息，要边界）
  客户端 -> 服务端：SEND（可配 inline，43 章约 14% 延迟收益）
  服务端预投 recv WR 池 = 天然并发上限
  WR 用光 -> 客户端 RNR 或自己限流
  最省事的一层背压：队列深度本身就是限流器

数据路径（大块，要带宽）
  RDMA WRITE 到预注册的 slot ring
  必须配 credit：消费完一个 slot 归还一个
  环深按「最坏停顿」算（第 2 张表），不是按平均
  发送端按 credit 发，不要按「我觉得对端该读完了」发

失败与超时
  对端异常退出（Q35）：连接不会立刻断，靠心跳
  心跳用 SEND（有背压、有 CQE）；不要用 WRITE（无 CQE 可观测）
  RNR 是信号不是错误：用它区分「对端忙」和「对端死」

经验值
  recv WR 池：16~64 条/连接（覆盖 RTT 内请求数，42 章 Little's law）
  data credit：按 2~10 ms 最坏停顿折算（高速网络上会很大，见第 2 表）
  timeout：跨机架 14（67 ms）；同机架 8（1.05 ms）（42 章）
```

"心跳不要用 WRITE"这条值得单独记住：WRITE 的成功不产生接收端 CQE
（除非用 `WRITE_WITH_IMM`），所以你无法用它判断对端是否活着。
**一个不会给你反馈的动词，不能用来探测存活。**

## 常见错法，以及症状

| 错法 | 症状 |
| --- | --- |
| 用 WRITE 往固定 ring 写，不加 credit | 偶发数据错乱，所有计数器正常 |
| 靠"加大 ring"解决覆盖 | 抖动一起来仍旧覆盖；1 ms 停顿要 47.7 MiB/连接 |
| 以为 PFC/DCQCN 能保护应用缓冲 | 网络零丢包，应用仍然读到半新半旧 |
| 用 WRITE 做心跳 | 永远探测不到对端死亡 |
| 用 RNR 当致命错误处理 | 把"对端忙"误判成"对端挂了"，误切换 |
| `rnr_retry=7` + SEND | 对端永不投 WR 时永久挂起（[42 章](./42-rdma-reliability-psn-window.md)） |
| 单机测试验证背压 | 测试里消费端不停顿，问题永远不出现 |
| credit 归还用"发送完成"而不是"消费完成" | 覆盖窗口仍在，等于没做背压 |

最后一条最隐蔽：credit 必须在**消费者真的处理完**之后归还，
不能在"数据到达"时归还。否则你的 credit 语义退化成"缓冲空着"，而不是"可以再写"。

## 模型边界

- 消费停顿建模为固定时长；真实抖动是长尾分布，需要按 p99 甚至 p999 算
- 排空速度设为 2.5× 线速；真实应用的追赶能力取决于 CPU 与下游
- 没有建模 PCIe、网卡内部缓冲、多连接共享同一个口
- 没有建模 PFC 反压对其他优先级的影响（[35 章](./35-rdma-congestion-control-loop.md) 讲过）
- 覆盖检测基于"slot 里还有未消费数据"；真实实现可能用序号校验，检出方式不同但代价相同
- 没有建模 DDR/内存带宽对 ring 读写的影响

4. credit 解决了什么、没解决什么？为什么环深加大后阻塞时间减少但吞吐不会超过消费者？
5. 四层流控各保护谁？哪一层能理解"消费者忙"？
6. IB 链路 credit 与 PFC 的本质区别是什么？为什么 PFC 必须留 headroom？
7. 为什么心跳不能用 WRITE？除了换 SEND 还有别的办法吗？
8. credit 应该在什么时刻归还？如果在"数据到达"时归还会怎样？

<details>
<summary>答案</summary>

1. 根本原因是**"谁决定写到哪里"**：SEND 的目标由接收端投 recv WR 时决定（接收端只在自己有空缓冲时才投），
   WRITE 的目标由发送端的 rkey 决定（接收端从未表态）。
   所以 SEND 天然带 application credit，WRITE 没有。
2. 发送端收到 `IBV_WC_SUCCESS`。因为 WQE 确实执行成功了——没有错误，只有结果不对。
   它最难查是因为所有计数器（丢包、重传、CQE 错误）都正常，必须从语义层入手。
3. **47.7 MiB / 连接**（12207 条 × 4 KB）；1000 条连接约 **47 GiB**。
   来源：400 Gbps = 50 B/ns，1 ms 就是 50 MB，缓冲必须装下停顿期间仍在到达的数据。
4. credit 解决**正确性**（不覆盖），不解决吞吐。环深加大只是"能偷吞更多突发"，
   欠账最终要靠追赶还回来；无论环多深，都不能超过消费者的处理能力。
5. 第 1 层链路 credit 保下一跳缓冲；第 2 层 PFC 保入口缓冲；第 3 层 DCQCN 保网络平均队列；
   第 4 层应用 credit 保接收端应用缓冲。**只有第 4 层能理解"消费者忙"**，前三层都不懂业务语义。
6. credit 是"收下才还信用"（精确计数，永不超发，不需要 headroom）；
   PFC 是"快满了才喊停"（信号有传播延迟，所以必须按"信号飞一个来回期间还能进来多少"预留 headroom）。
7. 因为 WRITE 的成功不给接收端产生 CQE（除非 `WRITE_WITH_IMM`），
   发送端无法用它观测对端是否活着。替代方案：`WRITE_WITH_IMM` 加一个需要预投 recv WR 的确认通道，
   本质还是回到了有背压的路径。
8. 必须在**消费者真正处理完**之后归还。如果在"数据到达"时归还，
   credit 的语义就退化成"缓冲空着"，而不是"可以再写"，覆盖窗口依然存在——等于没做背压。

</details>

## 一页速记

```text
核心语义（一句话）:
  SEND 的目标由接收端投 WR 时决定 -> 天然背压
  WRITE 的目标由发送端 rkey 决定  -> 零背压，写成功即 SUCCESS

零背压的后果（400G, slot 4KB, 线速 12.2 msg/us）:
  停顿 100us  -> 环深 256 覆盖 977 条
  停顿 1000us -> 环深 4096 覆盖 8123 条
  只有环深 >= 停顿期间写入量才归零
  应用看到的是「偶发数据错乱」，所有计数器正常

缓冲需求 = 线速 x 停顿（每连接）:
  1 ms  -> 47.7 MiB
  10 ms -> 476.8 MiB
  1000 连接 x 1ms = 47 GiB   <- 靠缓冲扛抖动不成立

两条路:
  A 限速（credit）        缓冲 = 环深（MB），覆盖 = 0，代价是阻塞
  B DCQCN 降速            只保网络，不保应用缓冲 -> 仍需要 A

四层分工:
  1 链路 credit  逐跳  纳秒  计数   保下一跳缓冲   不需要 headroom
  2 PFC          逐跳  微秒  信号   保入口缓冲     必须按延迟留 headroom
  3 DCQCN/ECN    端到端 毫秒 速率   保网络队列     不保证零丢包
```
