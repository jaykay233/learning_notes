## 为什么现在讲这个

到这里，[33–46](./33-rdma-six-layer-spine.md) 已经把每个机制单独算过了：
状态机、内存注册、可靠性、拥塞、背压、选型、性能模型。

但面试的最后一问通常是设计题：

> "给你一批机器，设计一个 RDMA 的 RPC / KV 存储，你会怎么做？"

这道题不难在"知道哪些机制"，难在**把它们排到一条路径上，并说清每处选型的依据**。
而且它有一个陷阱：初学者会说"用 RDMA 就快了"，
但下面三个数字会说明，**RDMA 让你快的那个东西，可能不是你想要的**：

```text
单边 READ 只比 RPC 快 3.5 us（RTT 占大头）
它真正的收益是：服务端 CPU 从 2 us/op 变成 0
代价是：一个 RTT 的正确性窗口，读错了也不会报错
```

这一章就用一个可运行的排队仿真 + 三条路径的账本，把 Q49/Q50 拆开。

## 心智模型：先分清"你优化的是延迟、吞吐，还是 CPU"

三条路径的差异不在延迟，而在**资源分布**：

```text
路径            延迟          服务端 CPU     正确性复杂度
SEND 请求/响应   1 RTT + 2 固定   2 us/op       低（服务端串行处理）
单边 READ        1 RTT + 固定     0            高（rkey 生命周期）
WRITE + credit   1 RTT + 固定     0（要归还 credit）  中（流控）
```

所以设计问答的第一步永远是同一个问题：

```text
我的瓶颈是 CPU、延迟，还是尾延迟？
  CPU 打满   -> 单边语义（READ / WRITE）
  延迟敏感   -> 压固定成本（46 章：固定占 58%）
  尾延迟敏感 -> 并发上限与排队（这一章第 1 节）
```

**"用 RDMA"不回答任何问题；"用 RDMA 的哪个动词、为了省哪个资源"才回答。**

## 一、RPC 的并发上限：它其实在决定尾延迟

RPC 用 SEND，服务端预投 recv WR，池深 W 就是并发上限。
这不是"性能参数"，是**排队系统里的服务台数量**：

脚本 [`47_rpc_kv_design_sim.py`](./47_rpc_kv_design_sim.py)：

```bash
cd ~/Downloads/learning_notes
python3 communication/47_rpc_kv_design_sim.py
```

```text
   W    到达 M/s     利用率   p50 us   p99 us        状态
   4      1.00     50%      1.8      9.6        空闲
   4      1.80     90%      5.5     45.2       有排队
   4      1.98     99%     45.7    166.3      接近饱和
  16      4.00     50%      1.6      9.3        空闲
  16      7.20     90%      2.6     13.6       有排队
  16      7.92     99%     13.3     42.9      接近饱和
  64     16.00     50%      1.6      9.2        空闲
  64     28.80     90%      1.8      9.7       有排队
  64     31.68     99%      6.0     15.5      接近饱和
 256     64.00     50%      1.6      9.2        空闲
 256    115.20     90%      1.6      9.3        有排队
 256    126.72     99%      2.6     10.3      接近饱和
```

（服务时间 2 us，M/M/W 排队）

三条读法：

1. **看绝对值，别看 p99/p50 比**。低负载时 p99/p50 本来就大（p50 只有 1.6 us），
   这个比值没有诊断价值。
2. **W=4 从半载到 99%，p99 从 9.6 us 涨到 166 us（17 倍）**，p50 只涨 25 倍但绝对值小。
   这是排队论的形状，不是实现 bug。
3. **加大 W 能把 p99 压回 10 us 量级**（W=256 时 99% 负载 p99 仍只有 10.3 us）。

但 W 不是免费的：

```text
每条 recv WR 占内存
CQ 深度必须 >= max_send_wr + max_recv_wr（34 章），否则静默丢 CQE
W 越大，错过一次唤醒的代价越大（尾延迟抖动）
```

所以"并发上限设多少"的正确答案是：**按 p99 目标反推，不是按吞吐反推。**

## 二、KV 的 GET：单边 READ 省的是 CPU，不是延迟

```text
                            路径      延迟 us    服务端 CPU ns     单核 ops/s
                  单边 RDMA READ       4.58             0    ∞（不占 CPU）
        RPC（SEND 请求 + SEND 回复）       8.08          2000         500K
                 RPC + 服务端缓存命中       6.58           500        2000K
```

（4 KB，RTT 3 us）

**延迟只差 3.5 us**——因为两条路都被 RTT 支配。
真正的差别在最后一列：

```text
1 M ops/s 需要 2 个核（RPC）-> 换成单边 READ 后需要 0 个核
```

**这就是 KV 用单边语义的全部理由：不是快，是省机器。**

面试里如果说"因为单边更快所以用单边"，会被追问"快多少"，
而答案 3.5 us 撑不起一个架构决策。正确的说法是：

> 单边 READ 把服务端从数据路径上摘掉了。延迟收益有限，
> 但服务端 CPU 归零，且不再需要为每次 GET 维护一个处理线程/队列。

## 三、代价：rkey 的正确性窗口

单边 READ 绕过了服务端，于是产生一个新的问题：

```text
服务端不知道谁在读、读到哪一刻
-> 释放一块 buffer 之后，可能还有客户端的 READ 在途
-> 如果立刻复用，客户端读到的是**新写入的内容**
-> 没有错误：合法内存、合法长度、错误内容
```

量一下这个窗口有多大：

```text
   目标 ops/s  RTT 3us slot    缓冲 KiB  RTT 500us slot    缓冲 MiB
     100000           0.5       1.8              50       0.2
    1000000           4.6      18.3             502       2.0
   10000000          45.8     183.3            5016      19.6
```

（slot 数 = 目标速率 × READ 在途时间 4582 ns）

### 两个反直觉的结论

**第一，内存不是主要代价。** 正常 RTT 下只有几十块 buffer（183 KiB）；
即使 RTT 抖到 500 us，10 M ops/s 也只有约 20 MiB。
所以"单边读很费内存"这个说法不成立。

**第二，真正的代价是一个时间窗口，而它只能靠 key 关闭，不能靠定时器。**

```text
方案 A：释放后等 5 us 再复用（定时器）
  -> 失败模式：某次 RTT 抖到 500 us，窗口被穿透
  -> 读到脏数据，无任何错误

方案 B：用 FRWR，READ 完成才 LOCAL_INV（39 章）
  -> 窗口由硬件保证关闭
  -> 代价：每次读都要拿一个 key，key 池深度 = 在途读数
```

**方案 B 是唯一正确的做法。** 这也解释了为什么
[39 章](./39-rdma-memory-registration-cost.md) 的 FRWR key 池深度
在 KV 场景里是硬约束：它必须覆盖在途 READ 数，否则会卡住而不是覆盖。

### 这就是 Q50 的答案核心

> 单边语义省 CPU，但把"生命周期管理"的复杂度
> 从"服务端串行处理"搬到了"客户端的并发假设"上。

账：省 2 us CPU/op，付出一个 RTT 的正确性窗口 + 可撤销 key 的复杂度。

## 四、PUT 路径：WRITE 必须配 credit

PUT 走 WRITE 看起来最自然（省服务端 CPU），但 [44 章](./44-rdma-flow-control-backpressure.md)
已经证明它**没有背压**：

```text
    停顿 ms        需要条数     容量 MiB          无 credit 的后果
      0.1        1220       4.8             静默覆盖未消费数据
      1.0       12207      47.7             静默覆盖未消费数据
     10.0      122070     476.8             静默覆盖未消费数据
```

所以 PUT 的设计不是"用不用 WRITE"，而是**credit 环挖多深**：

```text
环深 = 最坏停顿时长 x 线速 / slot 大小
400G 上 1 ms 停顿 = 47.7 MiB/连接
```

如果这个数字不可接受（多连接时确实不可接受），那只有两个选择：

```text
1) PUT 也走 SEND（回到有背压的路径，牺牲 CPU）
2) 接受限速：credit 用光就让发送端等（44 章证明这不会覆盖，只是变慢）
```

**没有第三条路。** 这是 [44 章](./44-rdma-flow-control-backpressure.md) 那个"缓冲 vs 限速二选一"在
系统设计层面的直接体现。

```text
    客户端                                          服务端
    ─────────────────────────────────────────────────────────────
    [1] 建连/换状态        RESET→INIT→RTR→RTS          34 章
    [2] 拿到 rkey（GET）   带版本与租约                  39/47 章
    [3] 填 WQE（inline）   350+150 ns                   43/46 章
    [4] 上线 + 交换机      传播 + 队列                  35 章
    [5] 单边 READ          ── 服务端不参与 ──            47 章
    [6] 产 CQE + poll      450 ns                       46 章
    ─────────────────────────────────────────────────────────────
    PUT 路径额外需要：
    [P1] credit 归还        环深 = 最坏停顿 x 线速        44 章
    [P2] 内存注册           FRWR/MW 而非每次 reg_mr      39 章
    [P3] 失败处理           RNR / flush / 心跳用 SEND     42/44 章
```

### 选型结论（Q49–Q53）

```text
请求/响应  -> SEND（有背压，天然并发上限）
大块读     -> 单边 READ（省服务端 CPU，代价是 rkey 生命周期）
大块写     -> WRITE + credit（省 CPU 但要自己做流控）
海量小消息 -> SEND + inline + batching + 多 QP（46 章）
CPU 是瓶颈 -> RDMA；协议要可改 -> DPDK（45 章）
小包多路径 -> 不要按包喷洒（45 章）
大消息     -> 大 MTU + 自适应路由可用（43/45 章）
```

## 常见错法，以及症状

| 错法 | 症状 |
| --- | --- |
| "用 RDMA 就快了" | 答不出快在哪；实测延迟只改善 3.5 us |
| 并发上限按吞吐算而不是按 p99 算 | 吞吐达标，p99 飙到 166 us |
| W 加大但不加深 CQ | 静默丢 CQE，低负载正常 |
| 单边 READ 用定时器保护 buffer 复用 | 偶发读到别人数据，无错误 |
| 认为单边读很费内存 | 实际 KiB 量级；真正的代价是正确性窗口 |
| PUT 用 WRITE 但不做 credit | 静默覆盖未消费数据 |
| GET 走 RPC 却说为了性能 | 真正的理由是省 CPU 或简化语义 |
| rkey 不复用（每次新 reg_mr） | 每 op 多几十 us，回到 39 章的 30% 税 |

## 模型边界

- 服务时间 2 us 是假设值；真实值取决于解析、查表、序列化
- M/M/W 假设指数服务时间与泊松到达；真实负载有突发与相关性，
  实际尾延迟通常比 M/M/W 更差
- 只建模服务槽，没有建模 CQ 轮询、线程唤醒、NUMA 跨 socket
- rkey 窗口按在途时间算，未包含客户端侧排队（真实窗口更长）
- credit 只按单连接算；多连接共享端口时还要考虑 PFC 反压（35 章）
- 没有建模副本、一致性协议与故障切换——那些是分布式层，不是 RDMA 层

最后一条边界很重要：**RDMA 只解决"搬数据"，不解决一致性与副本。**
设计题里如果把 RDMA 说成"KV 的完整方案"，是越界了。

<details>
<summary>答案</summary>

1. 决定**尾延迟**（p99）。W=4 从半载到 99% 负载，p99 从 9.6 us 涨到 166 us。
   按吞吐定会让 p99 失控；正确做法是按 p99 目标反推 W。
2. 只快约 **3.5 us**（4.58 vs 8.08 us，RTT 占大头）。
   真正的收益是**服务端 CPU 归零**：1 M ops/s 从需要 2 个核变成 0 个核。
3. "因为它把服务端从数据路径上摘掉了，省的是 CPU 不是延迟。"
   先纠正问题框架，再谈实现。
4. 释放的 buffer 在一个 RTT 内仍可能被读，读到的是新内容且**无错误**。
   不能靠定时器因为 RTT 会抖（p999 可能 500 us），窗口会被穿透；
   必须用 FRWR + `IBV_WR_LOCAL_INV`，让 key 失效由硬件保证。

6. 按"最坏停顿时长 × 线速 / slot 大小"算（44 章）。算出 47.7 MiB/连接时：

## 一页速记

```text
三条路径，比的不是延迟而是资源分布
  SEND 请求/响应   1 RTT + 2 固定   服务端 2 us/op   正确性复杂度低
  单边 READ        1 RTT + 1 固定   服务端 0         复杂度高（rkey 生命周期）
  WRITE + credit   1 RTT + 1 固定   服务端 0         中等（要做流控）

并发上限 = 排队系统的服务台数（M/M/W，服务 2 us）
  W=4   50%/90%/99% -> p99  9.6 / 45.2 / 166.3 us
  W=256 50%/90%/99% -> p99  9.2 /  9.3 /  10.3 us
  按 p99 目标反推 W，不要按吞吐反推
  W 大了 CQ 也要加深（>= max_send_wr + max_recv_wr）

单边 READ（4 KB，RTT 3 us）
  延迟 4.58 us vs RPC 8.08 us -> 只快 3.5 us
  收益：服务端 CPU 2 us/op -> 0（1 M ops/s 省 2 个核）
  代价：一个 RTT 的正确性窗口，读错也不报错
  -> 必须用 FRWR + LOCAL_INV 关窗口，不能靠定时器
  -> 隔离内存其实很小：10 M ops/s 仅 183 KiB（RTT 3us）/ 20 MiB（RTT 500us）

PUT 走 WRITE
  环深 = 最坏停顿 x 线速 / slot
  1 ms 停顿 @ 400G = 47.7 MiB/连接
  太大就只有两条路：改 SEND，或接受限速

设计题回答顺序
  1 瓶颈是 CPU / 延迟 / 尾延迟？
  2 选动词（SEND / READ / WRITE）
  3 算并发上限（p99）、算 credit（最坏停顿）、算 key 池（在途读数）
  4 说清代价换的是什么
```
