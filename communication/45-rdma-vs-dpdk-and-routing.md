## 为什么现在讲这个

Q51（RDMA 和 DPDK 怎么选）和 Q25（自适应路由和 ECMP 的差别）在题库里是两道孤立的题。
面试里也常被当成"背知识点"。但它们其实是**同一个思维方式的两次应用**：

> 两个技术看起来在竞争同一件事，实际上在优化**不同的资源**。
> 选错的代价不是"慢一点"，是"资源用错了地方"。

```text
RDMA vs DPDK     都在绕过内核，但一个花网卡的钱，一个花 CPU 的钱
自适应 vs ECMP   都在做负载均衡，但一个花"顺序"换"均衡"，一个不换
```

而第二组的代价，正好接回 [42 章](./42-rdma-reliability-psn-window.md)：
**乱序在 go-back-N 下等价于丢包。** 于是"更好的负载均衡"可能让带宽掉一个数量级。

这一章把两组都算出来，并且给出一个反直觉的结论：
**按包喷洒（自适应路由）在小包场景下比 ECMP 更糟。**

## 心智模型：先问"这个方案在花哪个资源"

两组题看起来毫无关系，但可以用同一个问句拆开：

```text
这个方案比那个方案快，快在"少花了哪个资源"？
被它省下的资源，是不是我当前的瓶颈？
```

套进去：

```text
RDMA vs DPDK
  RDMA 省的是 CPU cycles（协议在网卡执行）
  但它花网卡的钱：RNIC 更贵、VF/PFC 配置更复杂、传输层不可改
  -> 只有"CPU 是瓶颈、且不需要改协议"时，RDMA 才赢

自适应 vs ECMP
  自适应省的是"路径利用率"（能拆开一条流）
  但它花的是"包顺序"：per-packet 喷洒导致乱序
  -> 只有"乱序代价 < 均衡收益"时，自适应才赢
```

第二行后半句就是这一章的核心计算：**乱序在 go-back-N 下的代价可以高达 13 倍**
（[42 章](./42-rdma-reliability-psn-window.md)），
足以吃掉均衡带来的任何收益。

## 一、RDMA vs DPDK：CPU 到底花在谁身上

两者都绕过了内核协议栈，所以"RDMA 比 DPDK 快"这种说法没有信息量。真正的差别是**协议由谁执行**：

```text
DPDK:
  网卡 DMA -> 用户态轮询取包 -> 用户态解析 -> 用户态做 ACK/重传/拥塞 -> 拷贝
  CPU 成本随「你实现了多少协议」线性增长

RDMA:
  网卡 DMA -> 网卡自己做 ACK/重传/拥塞/可靠传输 -> 只在 CQ 里放一个 CQE
  CPU 只做：填 WQE + 敲 doorbell + poll CQE
```

脚本 [`45_rdma_vs_dpdk_and_routing.py`](./45_rdma_vs_dpdk_and_routing.py)：

```bash
cd ~/Downloads/learning_notes
python3 communication/45_rdma_vs_dpdk_and_routing.py
```

第一张表（3 GHz）：

```text
        方案  cycles/msg   us/msg      10M msg/s 需要核数
    内核 TCP       20000     6.67                66.7
      DPDK         600     0.20                 2.0
      RDMA         300     0.10                 1.0
```

**内核 TCP 要 66.7 个核才能做到 10M msg/s，RDMA 只要 1 个。**

这个 66 倍的差距不是"RDMA 更先进"，而是"内核 TCP 每笔消息要做 syscall + 协议栈 + 两次拷贝"。
DPDK 消掉了 syscall 和拷贝，但仍要在用户态跑协议。

### 加核有用吗

```text
        方案        1 核        8 核        64 核        瓶颈
    内核 TCP       0.1M       1.2M        9.6M       CPU
      DPDK       5.0M      40.0M      150.0M       CPU
      RDMA      10.0M      80.0M      150.0M        网卡
```

（网卡消息率上限按 150 M msg/s 计，[假设]）

**RDMA 加到 8 核就撞到网卡上限了。** 这不是"RDMA 扩展性差"，恰恰相反：
它说明单核已经足够，剩下的核可以去做业务逻辑。

而 DPDK 会一路线性涨到 64 核——代价是**这 64 个核被绑死在轮询上，无法超卖**。
在一个混部集群里，这意味着 64 个核的预算换 150 M msg/s，且不能跑别的任务。

### 一句话选型

> **RDMA 买"不用 CPU"，DPDK 买"可以改协议"。**

这个框架能直接回答所有变体：

```text
"只有以太网、没有 RNIC"        -> DPDK（RDMA 需要 RNIC）
"要自己改协议头"               -> DPDK（RDMA 传输层不可改）
"要极低延迟 + 低 CPU"          -> RDMA
"想省钱、CPU 富余"             -> DPDK
"要硬件级多租户隔离"           -> RDMA + SR-IOV（41 章：PD 不是墙）
```

两者也不冲突：很多系统用 DPDK 做控制面或自定义封装，用 RDMA 做数据面。

## 二、ECMP：逐流哈希的必然热点

ECMP 按**流**（五元组哈希）选路径。问题在于流是离散的：

```text
   16 条流 / 8 条等价路径，随机哈希 2000 次

   平均每条路径 2.00 条流
   最热路径负载  p50=4  p99=7  max=9
   最热路径 > 1.5x 平均 的概率：77.6%
```

**平均 2 条，p99 是 7 条——3.5 倍。** 这就是哈希碰撞，和算法好坏无关，
是"把 16 个球随机丢进 8 个桶"的数学性质。

### 大象流让问题变成结构性的

```text
     大象流数      被占路径         老鼠流可用路径         老鼠流可用带宽
        0         0               8           100%
        1         1               7            88%
        2         2               6            75%
        4         4               4            50%
        6         6               2            25%
```

**关键：逐流哈希无法把一条流拆到多条路径上。**

一条 400G 的大象流吃掉 1/8 的等价路径容量，其余所有老鼠流只能在剩下 7/8 里抢。
加再多老鼠流也补不回来——这是**结构性的**，不是概率性的。

这也解释了为什么训练集群和存储集群对 ECMP 的容忍度不同：
训练梯度同步是少量大流（[40 章](./40-rdma-collective-topology.md)），
一旦撞在一起就是硬热点；RPC 是海量小流，哈希能摊平。

## 三、自适应路由：用乱序换均衡

自适应路由（per-packet spraying）每包独立选路，绕开了"一条流只能走一条路"的限制。
代价是**同一流的包走了不同延迟的路径，到达顺序被打乱**。

```text
     延迟差 us     包间隔 us     包大小 B      乱序包数      乱序率
        0.1       0.08      4000      1218   6.09%
        0.1       0.50     25000         0   0.00%
        0.1       2.00    100000         0   0.00%
        0.5       0.08      4000     11420  57.10%
        0.5       0.50     25000         0   0.00%
        1.0       0.08      4000     13350  66.75%
        1.0       0.50     25000      3758  18.79%
        1.0       2.00    100000         0   0.00%
```

（4 条路径，延迟在 `[0, spread]` 上均匀铺开）

### 阈值行为：包间隔 vs 延迟差

这张表最重要的不是数字，是它的**形状**：要么 0，要么几十个百分点。

```text
判据：路径延迟差 > 包间隔  ->  相邻包互换顺序
包间隔 = 包大小 / 线速
  400G 下：4 KB = 0.08 us，25 KB = 0.5 us，100 KB = 2 us
```

所以：

```text
小包（RPC、All-to-All 的 token）  -> 包间隔极小 -> 必然乱序
大包（存储 IO、梯度分块）        -> 包间隔大于路径差 -> 几乎不乱序
```

**"自适应路由提升利用率"这句话必须带包大小。**

## 四、乱序的真实代价：接回 42 章

乱序本身不是问题——问题是 RC 用的是 go-back-N，只认累积 ACK：

```text
乱序到达的包 -> 接收端认为中间丢了 -> 丢弃乱序包（不缓存）-> 触发重传
```

于是**乱序 = 假丢包**，代价与真丢包完全相同（[42 章](./42-rdma-reliability-psn-window.md) 的放大系数）：

```text
      乱序率     W=32 放大     W=32 有效     W=256 放大    W=256 有效
    0.1%       1.016      393.5G        1.129      354.5G
    1.0%       1.165      343.3G        2.285      175.1G
    5.0%       1.825      219.2G        7.425       53.9G
   10.0%       2.650      150.9G       13.850       28.9G
   30.0%       5.950       67.2G       39.550       10.1G
```

**乱序率 10% + W=256：400G 只剩 28.9G。**

完整后果链：

```text
按包喷洒 -> 乱序 -> 接收端丢弃 -> go-back-N 重传 -> 带宽被自己吃掉
```

这就是为什么"更好的负载均衡"在 AI 集群里不一定更好：
如果你的工作负载是小包 + 大窗口，按包喷洒可能比 ECMP 的局部热点**更糟**。

### 两组题的共同结论

```text
RDMA vs DPDK:   都在绕过内核，但一个花网卡钱、一个花 CPU 钱
自适应 vs ECMP: 都在做均衡，但一个花顺序、一个不花
```

**技术选项很少是"更好/更差"，多数是"换一个资源付费"。** 面试里能说出"换的是哪个资源"，
比背参数有价值得多。

## 五、路由策略选择表

```text
                        场景                     选择             理由
        大量小包（RPC/All-to-All）               ECMP 或按流   按包喷洒会乱序，代价远大于均衡收益
                  少量大流（训练梯度）             自适应 / 按包喷洒   大流下乱序影响小，均衡收益大
                 大象流 + 老鼠流混跑              按流 + 拥塞控制   逐流哈希必然热点，靠 DCQCN 兜底（35 章）
                     对尾延迟极敏感           ECMP + 多路径备份   宁可有热点也不要乱序
                      存储大 IO            自适应 + 大 MTU   大包间隔大，乱序率低
```

注意最后一行的前提：**大 MTU 是"自适应路由可用"的前置条件**。
这和 [43 章](./43-rdma-l2-remaining-semantics.md) 的结论一致——MTU 不只是效率问题，
它决定了你能不能用按包喷洒。

## 常见错法，以及症状

| 错法 | 症状 |
| --- | --- |
| "RDMA 比 DPDK 快" | 答不出快在哪；实际上某些场景 DPDK 更合适 |
| 以为加核能线性提 RDMA 消息率 | 加到 8 核后无收益，误判为"软件没优化好" |
| 以为自适应路由总是更好 | 小包场景下带宽掉一个数量级 |
| 用按包喷洒跑 All-to-All | 乱序风暴，比 ECMP 的热点更糟 |
| 用 ECMP 跑少量大流 | 撞在一起形成硬热点，加路径也无效 |
| 只调 ECMP 哈希种子 | 只能改善平均，改不了"一条流只能走一条路" |
| 忽略 MTU 对路由策略的影响 | 小 MTU 下自适应路由不可用，却以为是配置问题 |
| 以为乱序是无害的 | 在 go-back-N 下等价丢包，放大系数按 W 增长 |

## 模型边界

- `cycles/msg` 是量级假设（内核 TCP 20000、DPDK 600、RDMA 300）；
  真实值取决于实现、批处理、CPU 微架构，但**排序关系**稳定
- 网卡消息率上限 150 M msg/s 是 400G 双口的假设值，不同代差很大
- ECMP 用均匀随机哈希模拟；真实哈希可能更好也可能更差（哈希极化）
- 自适应路由的乱序判据只考虑"延迟差 > 包间隔"，忽略缓存与交换机的重排
- 放大系数用 42 章的一阶近似 `1 + p(W+1)/2`，实测偏大（重传自身也会丢）
- 没有建模 selective ACK：如果协议支持 SACK，乱序代价会小得多，但 RC 没有

最后一条值得强调：**乱序的代价完全取决于"协议怎么处理乱序"。**
RC 用 go-back-N 所以代价极大；如果换成支持 SACK 的传输（比如某些用户态协议），
按包喷洒的代价会小很多。所以这个结论不是"自适应路由不好"，是"自适应路由与 RC 不匹配"。

## 自测

1. RDMA 和 DPDK 都绕过内核，那它们的差别到底是什么？一句话概括。
2. 为什么 RDMA 加核到一定数量后消息率不再提升？这说明它扩展性差吗？
3. 内核 TCP 要做到 10M msg/s 大约需要多少核？为什么？
4. ECMP 在 16 流 8 路径下，最热路径 p99 是平均的几倍？这是算法问题吗？
5. 为什么一条大象流就能吃掉 1/8 的路径容量？加更多老鼠流能补回来吗？
6. 自适应路由的乱序率为什么呈"要么 0、要么几十个百分点"的形状？
7. 乱序率 10%、W=256 时，400G 链路还剩多少？完整的后果链是什么？
8. 为什么"自适应路由更好"这个说法必须带包大小？

<details>
<summary>答案</summary>

1. **CPU 花在谁身上**：DPDK 让 CPU 在用户态执行协议，RDMA 让网卡执行协议。
   RDMA 买"不用 CPU"，DPDK 买"可以改协议"。
2. 因为瓶颈从 CPU 变成了网卡（PCIe/DMA/CQ 处理能力，假设 150 M msg/s）。
   这不说明扩展性差，反而说明**单核就够**，剩下的核定能做业务。
3. 约 **66.7 个核**（20000 cycles/msg @ 3 GHz）。因为每笔消息都要 syscall、
   走协议栈、做两次拷贝——这些是 CPU 的固定开销，与数据量无关。
4. **约 3.5 倍**（p99=7，平均=2）。不是算法问题，是"16 个球随机丢进 8 个桶"的
   数学性质；换更好的哈希只能改善平均，不能消除离散性。
5. 因为逐流哈希**无法把一条流拆到多条路径**。一条流只能占一条路径，最多占满 1/8。
   加更多老鼠流补不回来——被占掉的那条路径对它们不可用，这是结构性的。
6. 因为判据是"路径延迟差 > 包间隔"这个**阈值**，不是连续函数。
   包间隔由包大小决定（4 KB = 0.08 µs @ 400G），一旦跨过阈值，乱序率从 0 跳到几十个百分点。
7. 约 **28.9 Gbps**（放大 13.85 倍）。后果链：按包喷洒 → 乱序 → 接收端丢弃 →
   go-back-N 重传 → 带宽被自己吃掉。
8. 因为包间隔 = 包大小 / 线速。大包间隔大，超过路径延迟差就不会乱序；
   小包间隔极小，必然乱序。同一个路由策略在两种负载下结论相反。

</details>

## 一页速记

```text
RDMA vs DPDK（3 GHz，一条消息的 CPU）
  内核 TCP  20000 cyc = 6.67 us  ->  10M msg/s 要 66.7 核
  DPDK        600 cyc = 0.20 us  ->  2 核
  RDMA        300 cyc = 0.10 us  ->  1 核
  差别在「协议由谁执行」：DPDK 是 CPU，RDMA 是网卡
  加核：DPDK 线性涨到 CPU 上限；RDMA 8 核就撞网卡上限（不是缺点）
  一句话：RDMA 买「不用 CPU」，DPDK 买「可以改协议」

ECMP（逐流哈希）
  16 流 / 8 路径：平均 2，p99 = 7（3.5x），>1.5x 概率 77.6%
  大象流：1 条占 1/8 容量 -> 老鼠流可用带宽 88%
  逐流哈希无法拆分一条流 -> 热点是结构性的，不是概率性的

自适应路由（按包喷洒）
  阈值：路径延迟差 > 包间隔  ->  乱序
  4 KB @ 400G = 0.08 us   <- 小包必然乱序
  100 KB = 2 us           <- 大包几乎不乱序
  乱序 = 假丢包（42 章 go-back-N）
  乱序 10% + W=256 -> 放大 13.85x -> 400G 只剩 28.9G

选型
  小包 / RPC / All-to-All   -> ECMP 或按流
  少量大流 / 存储大 IO      -> 自适应 + 大 MTU
  大象老鼠混跑              -> 按流 + DCQCN 兜底

共同结论：每个选项都在换一个资源付费，问「换的是哪个」
```
