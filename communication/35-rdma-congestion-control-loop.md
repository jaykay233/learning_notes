## 为什么现在讲这个

[33 章](./33-rdma-six-layer-spine.md) 的 L4 把 DCQCN 讲成三步：交换机打 CE、接收端回 CNP、
发送端降速恢复。这句话没错，但它没回答任何运维真正要问的问题：

**`Kmin` 填多少？`Kmax` 为什么不等于 `Kmin`？`Pmax` 为什么是 0.1 而不是 1？**
**参数调错了，第一眼看到的现象是什么？**

没有这套东西，L4 就只是名词。更麻烦的是，[33 章](./33-rdma-six-layer-spine.md) 里
"PFC 管瞬时、DCQCN 管平均"这句话，如果不把**两级保险**的结构画出来，
很容易被理解成"两个可以互相替代的机制"——而现场大量故障正是这么配出来的。

这一章要把这条回路做成可算的：给一个队列、一组门限，算出队列会在哪里振荡、
PFC 什么时候被迫接管、以及为什么 400G 上无损比 100G 贵得多。

## 心智模型：两级保险，时间尺度差三个数量级

```text
微秒级 ────────────────────────────────────────────────
   PFC / credit      「现在就别发了」
   管：buffer 绝对不能溢
   手段：pause 帧，整条链路按停
   代价：反压传播、HOL、死锁、storm

毫秒级 ────────────────────────────────────────────────
   ECN + DCQCN       「以后少发一点」
   管：平均速率不超过公平份额
   手段：打标记 → CNP → 降速，逐流调整
   代价：收敛慢、参数多、短流被过度惩罚
```

**两层不是备份关系，是分工关系。** 调速器失效时保险丝还在，网络不会丢包——
这正是最危险的配置：**看起来一切正常，直到某一刻整片网络被 pause 按死。**

反过来，只有保险丝没有调速器（`Pmax=0`），你会得到一条"永不丢包但永远在停顿"的网络：
带宽利用率看起来还行，尾延迟完全是噪声。

## 闭环的四段，逐段看延迟

```text
[1] 交换机队列超过 Kmin → 按概率给包打 CE 标记
        ↓  随数据包一起到达接收端（不额外占带宽）
[2] 接收端看到 CE → 生成 CNP 回给发送端
        ↓  有速率限制，不能每包都回
[3] 发送端收到 CNP → 更新 alpha，速率乘以 (1 - alpha/2)
        ↓
[4] 一段时间没有 CNP → 定时器加性增，alpha 衰减
        ↓  回到 [1]
```

关键在于**每一段都有一次 RTT 量级的延迟**：

| 段 | 延迟来源 | 量级 |
| --- | --- | --- |
| [1]→[2] | CE 标记随包到接收端 | 0.5 RTT |
| [2]→[3] | CNP 回传 | 0.5 RTT |
| [2] 内部 | CNP 生成限速 | 几十 us |
| [4] | 加性增定时器 | 几十 us |

所以**一次完整的"发现拥塞 → 降速"闭环，至少是一个 RTT 加上 CNP 限速的间隔**。
RTT 5 us、CNP 限速 50 us 时，闭环时间约 55 us。在这 55 us 里，发送端按原速率继续灌，
队列还会再涨 `55 us × 线速率` = **687 KB**。

**这个数字直接决定了 `Kmax` 的下限**：如果 `Kmax - Kmin` 小于这段"闭环期间还会涨的量"，
标记还没来得及生效，队列就已经冲过 `Kmax` 了。

## 完整计算

脚本 [`35_congestion_control_loop.py`](./35_congestion_control_loop.py) 是一个离散时间闭环模拟：
2 个 DCQCN 发送端往同一个 100 Gbps 出口打，交换机 2 MB 缓冲、`xoff=1.5 MB`，
每 1 us 推进一次：注入 → 队列演化 → 按队列长度打 CE → 限速回 CNP → alpha 降速 / 加性恢复。

核心回路（摘自脚本，完整版见文件）：

```python
# [规范] DCQCN 标记函数：Kmin~Kmax 之间线性升到 Pmax
def ecn_prob(q):
    if q <= kmin:
        return 0.0
    if q >= kmax:
        return pmax
    return pmax * (q - kmin) / (kmax - kmin)

# 队列演化：注入 -> 排出 -> 溢出才丢
q += inject
out = min(q, BYTES_PER_US * dt)      # 100G = 12500 B/us
q -= out
if q > BUFFER_B:
    dropped += q - BUFFER_B
    q = BUFFER_B

# 标记与回传
p = ecn_prob(q)
ce_bytes = p * out
if rng.random() < p and (t - last_cnp) >= CNP_INTERVAL_US:
    alpha = alpha * (1 - G) + G              # G = 1/256
    rate = max(R_MIN, rate * (1 - alpha / 2))

# 没有 CNP 时加性恢复
elif (t - last_inc) >= RATE_INCREASE_US and (t - last_cnp) > RATE_INCREASE_US:
    rate = min(BYTES_PER_US, rate + RAI_BYTES_US * 8 * G)
    alpha = max(ALPHA_MIN, alpha * (1 - G))
```

## 第一件反直觉的事：goodput 区分不出配置好坏

四组配置的 goodput 全在 **100 Gbps 附近**，差不到 0.2%。

原因：发送端是 2x 过载的（两个发送端各自都能打满整条链路），所以哪怕被压到一半速率，
聚合流量仍然能填满出口。**带宽是最后才掉的东西，它不是灵敏指标。**

真正的判据是三列，各自回答不同问题：

| 指标 | 回答什么 | 极端配置下的表现 |
| --- | --- | --- |
| 队列均值 | 尾延迟有多差 | 过高：538 KB（排队 43 us） |
| PFC 暂停率 | 抗压能力还剩多少 | 过高：2.4%，再紧一点就靠 pause 活着 |
| 标记量 | 参数是否真的在生效 | 过高：0 M，说明 ECN 完全没参与 |

**这就是"现场看起来没事"的机制**：只盯带宽监控，四组配置一样好看；
但队列均值差了 180 倍，故障时一组能扛、一组直接崩。

顺带解释一个常见误判：`过高` 配置的暂停率只有 2.4%，很容易被判断成"PFC 很健康"。
但要看**绝对值**：2.4% 的暂停意味着这条链路靠 pause 活着，队列均值 538 KB
说明缓冲常年半满，任何一个 incast 或大流进来都会把它推过 `xoff`。

## 第二件：门限怎么定

三条约束，正好对应三个参数：

```text
Kmin  ≥ 若干 BDP（至少 1 个 RTT 的在途量）
        理由：Kmin 以下不标记，队列必须能吸收一个 RTT 的自然波动
Kmax  ≥ Kmin + 闭环期间还会涨的量
        理由：否则标记还没生效，队列已经冲过 Kmax
Pmax  ≈ 0.05 ~ 0.1
        理由：太高会让短流被过度惩罚，太低则收敛太慢
```

代入本模型的数字：

```text
BDP(100G, RTT 5us) = 12.5 KB/us × 5 us = 62.5 KB
闭环期间还能涨的量 = 55 us × 12.5 KB/us = 687 KB
```

所以 `Kmin` 至少要在 62.5 KB 以上（模型里 128 KB），
`Kmax - Kmin` 要能容纳接近 687 KB 的冲高——模型取 128→768 KB（差 640 KB）正好在这个量级。
这解释了为什么**别处抄来的门限值不能直接用**：它们背后是另一组 RTT 和链路速率。

## PFC 的两个数：quanta 与 headroom

### pause 帧到底停多久

quanta 的单位常被记错：**1 quanta = 512 bit times**，跟字节、帧长都无关。

```text
100 Gbps 下：1 quanta = 512 / 100e9 = 5.12 ns
最大值 65535 quanta  = 65535 × 5.12 ns = 335.5 us
```

**一条满值 pause 能把上游停住三百多微秒。** 这就是 PFC storm 的杀伤力量级——
不是"稍微慢一点"，是毫秒级抖动，比丢包重传（go-back-N，见 33 章）还难恢复。

### headroom：发 pause 到真停住，还在飞多少字节

这是 PFC 最贵的部分，也是最容易被"我们开了 PFC 所以无损"这句话掩盖的部分：

```text
headroom ≈ 2 × (单向延迟 × 线速率) + 2 × MTU
```

`2×` 的来源：pause 帧要传到上游（第一个延迟），上游停止前已经在发的包还要落地（第二个延迟）。

脚本第四张表：

```text
     链路       单向延迟 us    headroom KB
  100G           1.0             32
  100G           2.0             57
  100G           5.0            130
  400G           1.0            106
  400G           2.0            203
  400G           5.0            496
```

**400G + 2 us 单向延迟：单个端口单个优先级就要 203 KB 专用 headroom。**

算总账：32 端口 × 8 优先级 × 203 KB ≈ **51 MB**，全部用来防反压，还没算数据缓冲。
这就是 400G 上"无损"比 100G 贵得多的真实原因——**不是带宽贵，是 headroom 贵**，
而且它随线速率线性涨。

所以高速率集群必须用**共享 headroom / 动态 headroom**（按端口的动态使用情况分配），
而不是每个端口每个优先级静态预留。这也解释了为什么 400G 集群里
"按优先级隔离"这件事反而更难做——隔离的每个优先级都要独立付一份 headroom。

## 参数调错的症状对照

这张表是这一章最实用的部分。注意"第一现象"和"二阶症状"的区别：
第一现象是你在监控上直接看到的，二阶症状是它引发的连锁反应。

| 错误 | 第一现象 | 二阶症状 | 修正 |
| --- | --- | --- | --- |
| `Kmin` 太低 | 标记率长期偏高 | 队列很短但速率被压平，短流全被惩罚 | 抬高 Kmin 到 1~2 BDP |
| `Kmax` 太低 | 概率瞬间到 Pmax | 速率剧烈振荡，p99 抖动 | 拉开 Kmax−Kmin 到闭环涨量 |
| 两个都过高 | 几乎不标记（标记量≈0） | 队列涨到 xoff，PFC 暂停率升高 | 下调门限或减小 xoff |
| `Pmax` 太高 | 过度降速 | 带宽利用率低、收敛慢 | 降到 0.05~0.1 |
| `Pmax = 0` | ECN 完全失效 | 只剩 PFC，等价于只有保险丝 | 打开 ECN |
| CNP 间隔太密 | 连续打击发送端 | 速率长期贴地不恢复 | 拉开 CNP 限速间隔 |
| 加性增太快 | 恢复过猛 | 周期性锯齿，误标增加 | 减小 RAI 或延长定时器 |
| 忽略 RTT 差异 | 长短流同参数 | 长流被过度惩罚（同 CNP 下降更狠） | 按 RTT 分档或加权 |

最后一条容易被忽略但影响很大：**同等 CNP 数下，长 RTT 流恢复更慢**，
所以混合 RTT 场景里短流会占尽便宜，长流被系统性压制。这也是"跨机房 RDMA 很难调"的
一个结构性原因，跟参数填得好不好无关。

## 常见错法，以及症状长什么样

| 错法 | 现象 |
| --- | --- |
| 只开 PFC 不开 ECN | 监控里带宽满、丢包 0，但 p99 在毫秒级抖动；重启一次业务全挂 |
| 按端口静态预留 headroom 上 400G | 缓冲被 headroom 吃光，数据队列深度不足，反而更容易触发 pause |
| 门限从别的集群抄 | 网络"看起来"能用，但一上大流就队列打满（RTT/速率不匹配） |
| 用 goodput 验证调参 | 四组配置都是 100G，误判"都没问题" |
| 把 `xoff` 当数据缓冲用 | `xoff` 一大半是 headroom，实际数据队列只剩很小一截 |
| 只看 pause 计数不看时长 | 每秒几条满值 pause（335 us/条）被当成"偶尔抖动" |

倒数第二条是本章最值得带走的一条：**`xoff` 不等于"可用缓冲"**。
它的一个固定份额是 headroom（见上面的公式），链路越快那一份额越大。
所以"我买了 64 MB 缓冲，肯定够"这种判断在 400G 上会直接翻车。

## 模型边界，必须说清

这个模拟器**没有**建模：

- **short flow / incast**：短流被压速后没时间恢复，是 `Pmax` 的主要约束，本模型看不到
- **多跳与反压传播**：PFC 会沿链路逐跳传，本模型只有一跳
- **ECN 标记的随机性细节**：真实交换机按 WRED 式概率标记，不是按字节比例
- **DCQCN 的快速恢复 / 主动增两档**：这里合并成一个近似

所以它只能回答"参数调错长什么形状"，不能回答"该填多少"。
真实数值必须现场标定：看 `ECN 标记率`、`CNP 发送率`、`pause 帧速率`、
`队列长度直方图` 这四个，再反推。

2. `Kmax - Kmin` 的下界由什么决定？给出本模型里的算式。

4. 400G 上无损为什么比 100G 贵得多？给出 headroom 的算式和一组数字。
5. `xoff` 和"可用数据缓冲"是什么关系？为什么这个区别在高速率下致命？
6. 长短流混跑时，同样的参数下哪一类被压制？为什么？

<details>
<summary>答案</summary>

1. 因为发送端通常是过载的，聚合流量能填满出口；压到一半速率仍然打满线速。
   本模型四组配置的极差是 **0.2 Gbps**（99.8 ~ 100.0），完全无法区分。
   灵敏指标是队列均值（3K vs 538K）和 PFC 暂停率（0% vs 2.4%）。
2. 由"一次闭环期间队列还会涨多少"决定：
   `闭环时间 × 线速率 ≈ (RTT + CNP 限速) × 线速率 = 55 us × 12.5 KB/us ≈ 687 KB`。
   小于它会来不及收敛。
3. 只剩 PFC，等价于只有保险丝没有调速器：带宽满、丢包 0、监控全绿，
   但队列常年贴 `xoff`，尾延迟是毫秒级噪声，一次 incast 就可能引发 pause 传播。
4. `headroom ≈ 2 × 单向延迟 × 线速率 + 2 × MTU`。400G + 2 us → 203 KB（单端口单优先级），
   100G + 2 us → 57 KB。32 端口 × 8 优先级在 400G 下约 51 MB 只用于防反压。
   **贵的是 headroom，不是带宽**，且它随线速率线性涨。
5. `xoff` 里包含 headroom 这一固定份额，剩余才是可用数据缓冲。
   链路越快 headroom 越大（400G 单优先级就 200 KB 量级），
   所以"大缓冲"在 400G 上会被 headroom 吃掉大半，实际数据队列比名义值小得多。
6. 长 RTT 流被压制。同样次数的 CNP 降速后，它的恢复周期更长
   （加性增的速率与 RTT 成反比），所以公平性会系统性偏向短流。

</details>

## 一页速记

```text
两级保险（时间尺度差三个数量级）:
  PFC / credit   微秒级   buffer 不能溢   手段 pause 帧   代价 反压/死锁/storm
  ECN + DCQCN    毫秒级   平均速率要公平   手段 CNP 降速   代价 收敛慢/参数多

闭环四段，每段都有延迟:
  CE 标记(0.5 RTT) -> CNP 回传(0.5 RTT) + CNP 限速(几十 us) -> 降速 -> 加性恢复
  一次闭环 ≈ RTT + CNP 间隔
  闭环期间还会涨 = 闭环时间 x 线速率     ← Kmax-Kmin 的下界来源

三个门限怎么定:
  Kmin >= 1~2 BDP
  Kmax >= Kmin + 闭环涨量
  Pmax ≈ 0.05~0.1

指标分工（别用 goodput 验证）:
  goodput     最后才掉，不敏感
  队列均值     尾延迟
  PFC 暂停率   抗压能力
  标记量       参数是否生效

PFC 的两个数:
  1 quanta = 512 bit times     100G -> 5.12 ns，满值 335.5 us
  headroom ≈ 2 x 单向延迟 x 线速率 + 2 x MTU
  400G@2us -> 203 KB/端口/优先级    32x8 -> 51 MB

最容易翻车的一句:
  xoff 不等于可用缓冲，headroom 是固定份额，链路越快越大
```
