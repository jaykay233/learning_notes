### 为什么现在讲这个

题面写的是 `β = (XᵀX)⁻¹Xᵀy`，一眼看上去是几行矩阵乘，于是最容易得出的结论是「这题很水」。这个判断会直接导致三种错误，而且每一种都有具体代价：

- **把 `(·)⁻¹` 当成原子操作。** 在 PyTorch 里它是 `torch.linalg.solve`；在这里它是你要手写的一段严格串行代码，没有任何 GEMM 形态可以用。漏掉这一点，写出来的第一版会在 `p > 32` 时变成 1000 步串行。
- **在错误的维度上省 FLOP。** Cholesky 是 `0.20·p³` FMA，Gauss-Jordan 是 `0.53·p³`，前者省 2.7 倍 —— 但在 `p = 32` 时两者绝对值是 6448 与 17360 次 FMA，都是 0.1 µs 量级，而 Cholesky 之后的两次三角回代要吃掉 **4–6 µs 的纯延迟**。省 FLOP 的那个反而更慢。这就是本节 §6 的内容。
- **用 float32 裸算 Gram。** `XᵀX` 把条件数平方，`n = 1e5` 时 `‖δA‖/‖A‖ ≈ ε·√n = 3.8e-5`，传到解上是 `κ² × 3.8e-5`，容差 1e-2 直接不够。这个错误不会崩，只会「差一点点」，而差多少是可以提前算出来的（§5）。

所以本节的交付物不是「一段能跑的代码」，而是三样可以复用的东西：一个**不用 GPU 就能跑的索引仿真**（它第一次跑就抓到了一个真 bug）、一个**κ² 预测判据**（拿到测试形状就能判它会不会挂）、以及一套**按延迟而非按 FLOP 选算法**的推理。

## 1. 完整公式与三种解法

题目给的闭式解：

\[
\hat\beta = (X^\top X)^{-1} X^\top y
\]

工程上要把它读成「解正规方程」，不是「先求逆再乘」：

```text
A = XᵀX        （p×p，对称正定，代价 p²n）
b = Xᵀy        （p，代价 pn）
解 A β = b     （代价 p³ 量级的求解，而不是 2p³ 的求逆）
```

| 解法 | FLOP（`p=32`） | 串行深度 | 用在本题？ |
|---|---|---|---|
| Gauss-Jordan 求 `A⁻¹` 再乘 | `2p³` ≈ 65 K | `p` 步 | 不选：白算一个逆矩阵 |
| Cholesky + 两次三角回代 | `0.20·p³` = 6,448 | `p` 步逐元素 + `2p` 步**归约** | 最初的实现（§6 说明为何换掉） |
| **Gauss-Jordan 直接消 `[A\|b]`** | `0.53·p³` = 17,360 | `p` 步，每步全并行，零归约 | **最终选择** |
| Householder QR | `2np² - 2p³/3` | 分块并行 | 不需要：`κ ≲ 400` 时正规方程够用 |

`p = 32` 那一列的意义在于：三者都在 10⁴～10⁵ 次 FMA，在 203 GFLOP/s 的单个 SM 上都是 **0.1 µs 量级**。**在这个尺度上比 FLOP 是没有意义的**，能比的只有串行深度和同步次数。这是本节的主线。

## 2. 规模分档：这道题其实是两个问题

题面最容易被跳过的是最后一行：**Performance is measured with n_features = 32, n_samples = 32**。而约束里的上界是 `n = 100000, p = 1000`。这两端的最优实现不可能一样：

| | `p = n = 32`（计时形状） | `p = 1000, n = 1e5`（约束上界） |
|---|---|---|
| Gram FLOP | `p²n` = 3.3e4 | `p²n` = 1e11 |
| 求解 FLOP | `0.53p³` = 1.7e4 | `0.53p³` = 5.3e8 |
| 谁主导 | **kernel launch（3–5 µs）** | **X 的访存（400 MB）** |
| 求解占比 | 25% | 0.3% |

`p=1000` 时 Cholesky 只占 0.3%，`A` 是 4 MB 装不进 48 KB 的 smem，必须分块；`p=32` 时 launch 占 90%，要的是**一次 launch 做完所有事**。

本实现选择只做后者（`p ≤ 32`）。这个上限不是随便定的：「一个线程一个输出」意味着 `p²` 必须 ≤ 1024，而线程数上限正是 1024。**这个映射本身就把上限钉死在 32。** 超出时 `solve()` 直接返回、不写 `beta`。

## 3. 单 kernel 的时间账

`p = n = 32` 的全部数学：

| 阶段 | 算式 | FMA |
|---|---|---|
| `A = XᵀX` | `p²n = 32³` | 32,768 |
| `b = Xᵀy` | `pn` | 1,024 |
| GJ 消元 | `0.53p³` | 17,360 |
| **合计** | | **≈ 51,200 FMA ≈ 10.2 万 FLOP** |

```text
单 SM FP32 峰值 = 8.14 TFLOPS / 40 SM ≈ 203 GFLOP/s
数学时间       = 8.9e4 / 203e9 ≈ 0.44 µs
一次 launch    = 3–5 µs
```

**拆成三个 kernel（Gram / 求解 / 写回）会让 90% 的时间花在 launch 上。** 所以整个算子的设计目标不是「算得快」，而是「只发一次 launch，所有中间量留在 smem」。

```text
smem 预算：
  A  32 × 32 × 4B = 4096 B     （Gram 之后原地变成消元中的矩阵）
  b  32 × 4B      =  128 B
  合计            = 4224 B     （T4 每 SM 有 48 KB 可用，用掉 9%）
```

注意 `STRIDE = MAXP` 没有 +1 填充。这是 Gauss-Jordan 白拿的好处：它只做**行访问**（warp 内 `j` 连续），不存在按列跨行读的指令。Cholesky 的 rank-1 更新要读 `A[j][c]`（`j` 是 lane、`c` 固定），那是列访问，缺填充就是 32 路 bank conflict（§6）。

## 4. 索引映射：一个线程一个输出

```text
blockDim = (1024)         一个 block
i = tid >> 5  ∈ [0,32)    A 的行号 = warp 号
j = tid & 31  ∈ [0,32)    A 的列号 = lane 号
线程 (i,j) 负责 A_ij = Σ_k X[k][i]·X[k][j]
```

这个映射的代价和收益都在同一条访存指令上：

```text
warp 内 j 连续、i 固定
  → xj = X[·][j]     沿 lane 连续 32 个 float = 一条 128 B cache line，完美合并
  → xi = X[·][i]     32 个 lane 读同一地址，硬件广播，1 个事务
  → 32 个 warp 读的是同一行，靠 L1 命中，DRAM 只走一遍
```

`b = Xᵀy` 不需要单独一遍。warp 0 的 lane `j` 手里已经有 `xj = X[·][j]`，顺手累加 `xj·y[k]` 即可 —— 全局只多读一条 `y`（`n × 4B`），不重读 `X`。这是纯赚：少了 `p·n` 次重复读，也就是少了 32 倍。

## 5. Gram 的精度：float 段内 + double 段间

设 `A_ij = Σ_k x_ki·x_kj`，共 `n` 项。fp32 串行累加时部分和是随机游走，量级 `√j·σ²`，舍入误差累计

\[
\delta A \approx \varepsilon \sum_j \sqrt{j}\,\sigma^2 \approx \varepsilon\, n^{1.5}\sigma^2
\]

而 `‖A‖ ≈ n·σ²`，于是

\[
\frac{\|\delta A\|}{\|A\|} \approx \varepsilon\sqrt{n}
\]

`n = 1e5` 时是 **3.8e-5**。正规方程把条件数平方，传到解上：

```text
误差 ≈ κ(X)² × ε√n = 133² × 3.8e-5 ≈ 6.7e-1   ← 远超 1e-2
```

修法不是换 double 全算（T4 的 FP64 是 FP32 的 **1/32** 速率，`p²n = 1e8` 次 DFMA 落到单个 SM 上要 31 ms，而 Gram 本身访存只要 1.6 ms），而是**分段**：

```cuda
for (int k0 = 0; k0 < n; k0 += CHUNK) {          // CHUNK = 256
    float pa = 0.0f;
    for (int k = k0; k < k1; ++k) pa = fmaf(xi, xj, pa);
    accA += pa;                                   // 每 256 项一次 double 加
}
```

把上面公式里的 `n` 换成 `C = 256`：`‖δA‖/‖A‖ ≈ ε√C = 1.9e-6`，放大后 `κ² × 1.9e-6` 的理论上界是 `3.2e-2`，实测落在 `2.2e-3`（§7.3 表）——上界偏保守约一个数量级，方向上是对的。代价是 `n = 1e5` 时 390 次 double 加，相对 1.6 ms 的访存可以忽略。

**这就是那个「用 float 还是 double」问题的正确答案：两个都用，按段分开。** 段内要吞吐所以用 float，段间只有 390 次所以用 double。

## 6. 求解器：Cholesky 的串行代价，与为什么换成 Gauss-Jordan

### 6.1 第一版：Cholesky + 两次三角回代

`A = LLᵀ`（right-looking，原地）：

```cuda
for (int c = 0; c < p; ++c) {
    if (tid == 0) A[c*STRIDE+c] = sqrtf(fmaxf(A[c*STRIDE+c], 1e-30f));
    __syncthreads();
    const float dcc = A[c*STRIDE+c];
    if (j == 0 && i > c && i < p) A[i*STRIDE+c] /= dcc;      // 列归一化
    __syncthreads();
    if (j > c && i >= j && i < p)                            // rank-1 更新
        A[i*STRIDE+j] -= A[i*STRIDE+c] * A[j*STRIDE+c];
    __syncthreads();
}
```

然后两次三角回代。`p ≤ 32` 正好一个 warp，于是可以只用 `__syncwarp()`：

```cuda
if (warp == 0) {
    for (int r = 0; r < p; ++r) {                    // 前代 L z = b
        float v = (lane < r) ? A[r*STRIDE+lane] * z[lane] : 0.0f;
        v = warp_sum(v);                              // 5 级 __shfl 归约
        if (lane == 0) z[r] = (b[r] - v) / A[r*STRIDE+r];
        __syncwarp();
    }
    /* 回代对称 */
}
```

注意这一版的 `STRIDE` 必须是 `MAXP + 1 = 33`：rank-1 更新里的 `A[j*STRIDE+c]`（`j` 是 lane、`c` 固定）是**列访问**，缺填充就是 32 路 bank conflict。换成 GJ 之后这个需求消失了，因为 GJ 全程只做行访问。

### 6.2 这份代码的问题：不是 FLOP，是 64 次串行归约

| | Cholesky + 回代 | Gauss-Jordan |
|---|---|---|
| FMA | 6,448 | 17,360（2.7×） |
| 除法 | 560 | **32** |
| `sqrt` | 32 | **0** |
| `__syncthreads()` | 3p = 96 | p = 32（不归一化） |
| **串行归约** | **2p = 64 次** | **0 次** |
| 每步并行度 | 收敛到 1（回代） | 恒定 `p²` |

一次 5 级 `__shfl` 归约的延迟约 100–150 cycles（每级 20–30），64 行就是 **6000–9500 cycles ≈ 4–6 µs**，而这段时间里 63/64 个 warp 完全空转。相比之下 GJ 多出来的 10,912 次 FMA 摊到 1024 个线程上是每个线程 11 次，不到 40 cycles。

附带的量级差异也值得记：**除法从 560 次降到 32 次，`sqrt` 从 32 次降到 0 次。** T4 上一次除法约 20 cycles（走特殊功能单元），560 × 20 = 11200 cycles。**在这个尺度上，除法次数比 FMA 次数更有分量。**

**结论：在 `p = 32` 上，省 FLOP 的算法比多算 FLOP 的算法慢 4 倍。** 判据不是 FLOP，是「有没有长度为 p 的串行归约」。

### 6.3 最终实现：不归一化主元行的 Gauss-Jordan

第一版 GJ 是「先归一化第 `c` 行，再消去」：

```cuda
if (i == c) {                       // 归一化，只有 warp c
    const float piv = A[c*MAXP+c];
    __syncwarp();                   // lane c 马上要写它，先让所有 lane 读完
    const float inv = 1.0f / piv;
    if (j >= c && j < p) A[c*MAXP+j] *= inv;
    if (j == 0)          b[c] *= inv;
}
__syncthreads();
```

这里有 `__syncwarp()`，而这句在 numpy 仿真里**根本不存在**（numpy 是串行的，没有竞争），所以它对不对只能靠审代码。最终版把它整个消掉了 —— 方法是不归一化，改缩放乘数：

```cuda
for (int c = 0; c < p; ++c) {
    const float inv = 1.0f / A[c * OLS_MAXP + c];   // 所有线程广播读，无写入者

    if (row != c && row < p) {
        const float f = A[row * OLS_MAXP + c] * inv;      // f = A[i][c]/A[c][c]
        if (col > c && col < p)
            A[row * OLS_MAXP + col] -= f * A[c * OLS_MAXP + col];
        if (col == 0)
            b[row] -= f * b[c];
    }
    __syncthreads();
}
// A 现在只剩对角，beta[i] = b[i] / A[i][i]
if (row == 0 && col < p) beta[col] = b[col] / A[col * OLS_MAXP + col];
```

**为什么这样就安全：第 `c` 步里没有任何线程写 row `c`。** 归一化的版本必须写 `A[c][c]`（除以主元），所以读主元和写主元挤在同一个同步区间里；不归一化的版本让 `A[c][c]` 只读不写，竞争就消失了。

代价与收益：

| | 归一化版 | 不归一化版 |
|---|---|---|
| `__syncthreads()` | 2p = 64 | **p = 32** |
| `__syncwarp()` | 1 次/步（32 次） | **0** |
| 精度（§7.2） | 基准 | 等价（差异在累加顺序噪声内） |

三个必须注意的点：

1. **`A[c][c]` 在后续步骤里不会再被写。** 第 `c' > c` 步只更新 `j > c'` 的列，而 `A[c][c]` 的列号是 `c`，所以 `c < c'` 时它已经出局。这是「不归一化」能成立的前提。
2. **消元后不把 `A[i][c]` 写回 0。** 所有 `i != c` 的线程都要读它当乘数，而 `(i,c)` 线程若同时写 0 又是一个竞争。第 `c` 列在后续步骤里不再被访问，留着无害。**少一次写，少一个竞争面。**
3. **只更新 `j > c`。** `j < c` 的列早已消完，是死数据。

**这条经验可以推广：把「写共享内存」的那一步从关键路径上拿掉，往往比加一个同步原语更划算。** 归一化看起来是省了除法，实际上是给每一步塞进一个必须同步的写。

### 6.4 数学推导：为什么这个算法是对的、且是稳定的

#### 6.4.1 单步 = 一次秩 1 更新

第 `c` 步用第 `c` 行清掉其他行第 `c` 列。设主元 `p_c = A⁽ᶜ⁾_cc`、乘数 `f_i = A⁽ᶜ⁾_ic / p_c`（`i ≠ c`）、`f_c = 0`，取

```
E_c = I − f·e_cᵀ      （f 是列向量，e_c 是第 c 个单位基向量）
```

作用到第 `i` 行：

```
e_iᵀ E_c A⁽ᶜ⁾ = row_i(A⁽ᶜ⁾) − f_i · row_c(A⁽ᶜ⁾)

⇒  A⁽ᶜ⁺¹⁾_ij = A⁽ᶜ⁾_ij − f_i·A⁽ᶜ⁾_cj
    b⁽ᶜ⁺¹⁾_i  = b⁽ᶜ⁾_i  − f_i·b⁽ᶜ⁾_c
```

`i == c` 时 `f_c = 0`，所以**第 `c` 行原地不动** —— 这正是「不归一化」的代数表述。

#### 6.4.2 不变式归纳：只需更新 `j > c`

不变式：进入第 `c` 步时，所有 `j < c` 的列已清空（`A⁽ᶜ⁾_ij = 0` 对 `j < c, i ≠ j`）。归纳步证明第 `c` 步之后清到 `j ≤ c`：

```text
情况 A  j = c（清理目标）：
        A⁽ᶜ⁺¹⁾_ic = A⁽ᶜ⁾_ic − (A⁽ᶜ⁾_ic/p_c)·p_c = 0                    ∎
情况 B  j < c（不能弄脏已清空的列）：
        A⁽ᶜ⁺¹⁾_ij = 0 − f_i·A⁽ᶜ⁾_cj = 0 − f_i·0 = 0                   ∎
                    ↑不变式        ↑j<c 且 c≠j，故 (c,j) 是非对角位
```

关键在情况 B：**清第 `c` 列对第 `j` 列的副作用恰好是 `f_i × 0 = 0`**，所以左到右扫一遍就够。

由此 `j` 的三种情况：

| `j` | 更新结果 | 做不做 |
|---|---|---|
| `< c` | `0 − f_i·0 = 0`，值不变 | 不用 |
| `= c` | 恒为 `0`，且此列此后不再被读 | 不用 |
| `> c` | 真更新 | 必须 |

省掉的量是 `(p²/2)·(p−1) ≈ p³/2` FMA —— **不做这个裁剪，GJ 代价直接翻倍**（`p³/2 → p³`）。

#### 6.4.3 终点与两条副产品

```
A⁽ᵖ⁾ = E_{p−1}···E_0·A = D（对角）   ⇒   β_i = b⁽ᵖ⁾_i / D_ii
```

因为 `det(E_c) = det(I − f e_cᵀ) = 1 − f_c = 1`（秩 1 扰动行列式引理），所以

```
det(A) = det(D) = ∏ D_ii        A⁻¹ = D⁻¹ E_{p−1}···E_0
```

实测印证：`p=4` 时 `prod(diag) = 75910312.65583304`，`det(A) = 75910312.65583298`。
第二式说明**「求逆」与「解方程」在 GJ 里是同一个过程**，这正是 GJ 比 LU 贵的根源：LU 分解完还要单独做两次回代，GJ 把右端项一起消掉了。

#### 6.4.4 稳定性：对 SPD，增长因子恰好为 1

**定理**：SPD 矩阵上 GJ 无选主元的增长因子 `≤ 1`，中间矩阵任何元素都不超过初始最大元素。

**证明**三步。

```text
① 每个中间矩阵都是 Schur 补，因而仍是 SPD
   把 A⁽ᶜ⁾ 的第 c 行/列换到首块：[ a  bᵀ ; b  M ]
   A⁽ᶜ⁺¹⁾ 的 trailing 部分 = M − b bᵀ/a = Schur 补
   SPD 的 Schur 补仍是 SPD ⇒ 归纳成立

② SPD 的非对角元被对角元控制（M-内积下的 Cauchy–Schwarz）
   |M_ij| = |⟨e_i, e_j⟩_M| ≤ sqrt(M_ii · M_jj)

③ 对角元单调不增
   A⁽ᶜ⁺¹⁾_ii = A⁽ᶜ⁾_ii − (A⁽ᶜ⁾_ic)² / A⁽ᶜ⁾_cc  ≤  A⁽ᶜ⁾_ii
```

三步合起来：

```
|A⁽ᶜ⁾_ij| ≤ sqrt(A⁽ᶜ⁾_ii·A⁽ᶜ⁾_jj) ≤ sqrt(A⁽⁰⁾_ii·A⁽⁰⁾_jj) ≤ ||A||₂
⇒ 增长因子 ≡ max|A⁽ᶜ⁾| / max|A⁽⁰⁾| ≤ 1
```

实测（`p = 8..64`，各 20 组随机 SPD）：**全部精确等于 `1.000000`**，不是「约等于」。
这就是**不需要选主元**的原因，与 Cholesky 不需要选主元完全同源。

#### 6.4.5 悖论：乘数涨到 7.6e5，矩阵却没长大

同一组实验里：

```
eps=     0   kappa(X)=       3.3   max|f| =       0.43
eps=   0.1   kappa(X)=      14.8   max|f| =      41.79
eps=  0.01   kappa(X)=     162.0   max|f| =    4358.87
eps= 0.001   kappa(X)=    2040.3   max|f| =  755960.98
```

乘数可以大到 75 万而元素一动不动。原因是 **`f_i` 与 `A_cj` 的乘积有界**：

```
|f_i| = |A_ic|/A_cc  ≤  sqrt(A_ii/A_cc)          ← ②
|f_i·A_cj| = |A_ic·A_cj|/A_cc
           ≤ sqrt(A_ii·A_cc)·sqrt(A_cc·A_jj)/A_cc = sqrt(A_ii·A_jj) ≤ ||A||
```

**无界的乘数 × 相应变小的第 `c` 行 = 有界的更新量。** 更新 `A_ij − f_i·A_cj` 是一次**灾难性相消**，有效位大量丢失。

这解释了误差的真正来源，也解释了为什么粗糙界毫无用处：

```text
粗糙上界  ||E_c||∞ 累乘 = 2.27e+21   （p=32）
实测误差                 = 2.66e+03   （= κ²）
```

差 18 个数量级。**任何基于 `||E_c||` 的界都注定悲观，因为它看不见相消。** 正确框架是「后向稳定 + 条件数」：由 §6.4.4 算法后向稳定（增长因子 = 1），所以前向相对误差 ≈ `κ(A)·ε`，而正规方程再把 `κ` 平方一次 → `κ(X)²·ε`。这正好是 §7.3 实测到的东西。

## 7. 两个实测到的 bug（都在写 CUDA 之前被抓到）

### 7.1 Cholesky 的 rank-1 更新漏了对角

第一版写的是 `i > j`（只更新严格下三角）。仿真立刻报：

```text
    32x32  kappa=34.5  judge_err=5.75e+01  FAIL
```

数学上第 `c` 步要做的是「整个 trailing 子矩阵减去 rank-1 项」，包括对角：

```text
A[i][j] -= L[i][c]·L[j][c]     对 i ≥ j > c
```

对角项是 `A[j][j] -= L[j][c]²` —— **一次平方，不是两次相减**，没有任何「减重」可言。写成 `i > j` 会让对角永远保持 Gram 的原始值，也就是 **Schur 补从未被形成**：第 `j` 步开方时取到的数偏大，`L` 的整条下游全错。

症状值得记住：**不崩、不 NaN、不出现整带为 0**，只是误差从 `3e-4` 跳到 `5e+1`。这种错误 `max abs diff` 定位不了，只能靠逐索引仿真或者审代码。

### 7.2 换算法之后精度反而没坏

`Gauss-Jordan` 理论上比 Cholesky 的误差常数大一点，实测基本等价，有一个用例还更好：

| 形状 | Cholesky | Gauss-Jordan |
|---|---|---|
| `32×32`，`κ=133` | 2.35e-03 | 4.73e-03 |
| `8×8`，`κ=105` | 6.21e-03 | 9.46e-03 |
| `1000×32`，`κ=1.4` | 2.14e-06 | 2.86e-06 |
| `ε=3e-2`，`κ=394` | 4.17e-01 | **8.08e-03** |

（同一份 Gram 输出、同一条随机序列，由 `ols_emul.py` 一次跑出，保证可复现。）

原因：Cholesky 多一个 `sqrt`、多一段误差传播（先算 `L` 再解两次），GJ 直接一步到 `b`。**「更省的算法精度更好」在这里不成立，两者都只受 `κ²` 支配。**

### 7.3 完整精度表（`ols_emul.py` 的实测输出）

```
       n×p     κ(X)      κ²·ε |         GJ   Cholesky
    1×1        1.00  1.20e-07 |   1.52e-06   2.92e-06
```

## 8. 验证：不开 GPU 的索引仿真

`ols_emul.py` 把 `ols.cu` 的三个阶段拆成三个可独立调用的函数（`gram` / `gj_solve` / `chol_solve`），阶段 2 的两种解法都实现了，所以 §7.2 的对照表是同一份 Gram 输出跑出来的：

```python
def gj_solve(A0, b0, p):
    A, b = A0.copy(), b0.copy()
    for c in range(p):
        inv = f32(1.0) / A[c, c]               # 2a 归一化第 c 行
        for j in range(c, p):
            A[c, j] = f32(A[c, j] * inv)
        b[c] = f32(b[c] * inv)
        for i in range(p):                     # 2b 消去其余各行
            if i == c:
                continue
            f = A[i, c]
            for j in range(c + 1, p):
                A[i, j] = f32(A[i, j] - f32(f * A[c, j]))
            b[i] = f32(b[i] - f32(f * b[c]))
        # 不写回 A[i][c]：第 c 列此后再不被读，写它反而构成竞争
    return b[:p]
```

两条纪律缺一不可：

1. **每个标量运算都显式 `f32(...)`。** numpy 默认 float64，不写就会把要测的误差悄悄抹掉，仿真通过而 CUDA 不通过。
2. **仿真的是索引，不是性能。** 它不能告诉你快不快，只能告诉你对不对。**「先仿真再写 CUDA」的收益只在索引和数值，不在时间。**

这个脚本的价值已经被兑现过一次（§7.1）：bug 在写 CUDA 之前就被抓到了，省掉的是「在 T4 上对着 `5.75e+01` 猜是 tiling 还是精度」的那几轮。

## 9. 运行与边界

```bash
# 不需要 GPU：验证数学、索引、精度判据
python ols_emul.py

# 需要 T4：与 float64 正规方程对拍 + 计时

python ols_check.py            # 加 --big 会多跑 n=100000
```

### 9.1 交付版本刻意避开的写法

提交到在线判题时遇到过一次 `1 error detected in the compilation`，但拿不到具体报错。为了排除可能性，最终版把所有「可能因环境不同而报错」的构造都去掉了：

| 去掉的 | 原因 |
|---|---|
| `namespace { }` + `constexpr` | 匿名命名空间的成员在全局 `extern "C"` 函数里可见性依赖隐式 using-directive，标准上没问题，但老编译器/严格模式下不值得赌 |
| `__ldg`、`fmaf` | 需要 `device_functions` 系列的声明；普通下标访问 + `a*b+c` 由编译器自动生成 LDG/FFMA |
| `__restrict__` | 不影响正确性，但和 `-Werror` 组合时可能触发警告 |
| `__syncwarp` | §6.3 换成不归一化的写法后不再需要，也就消除了「arch 版本差异」这个变量 |
| `__launch_bounds__` | `(1024, 1)` 本来就不约束任何东西 |
| **非 ASCII 注释** | `ᵀ`、`κ`、`≈` 这些字符如果被判题系统重新编码，可能变成非法字节序列。**这是最可能的元凶之一，也是最容易验证的** |

最后一条值得单独强调：**代码里除了中文注释以外的一切都可疑**。改成纯 ASCII 注释后，文件里 `ord(ch) > 127` 的字符数为 0，这一类失败原因就被彻底排除了。

| 边界 | 行为 |
|---|---|
| `p > 32` | 直接返回，**不写 `beta`**（`p² > 1024` 放不进一个 block） |
| `p = 1` | 退化为 `β = Xᵀy / XᵀX`，走完整流程 |
| `A[i][i] = 0` | `1.0f/0.0f = inf` → 输出 NaN。题面保证 full rank，这里选择**响亮失败**而不是悄悄返回垃圾 |
| `κ(X) > 400` | 精度不足（§7.3），需要换 double 或 QR |
| `n = 1e5, p = 32` | 可用。Gram 是单 SM 上的 L1 带宽受限，约 2 ms 量级（未实测） |

`p > 32` 时的正确做法是分块：Gram 走 `32×32` tile 网格（`p²/1024` 个 block），求解走 32 宽的 panel + TRSM + SYRK 的分块 Cholesky。那是另一套代码，本笔记不含。

## 10. 自检

**Q1.** `Cholesky` 比 `Gauss-Jordan` 少 12 倍 FLOP，为什么在 `p=32` 上反而更慢？

<details><summary>答案</summary>

因为 `p=32` 时两者的绝对 FLOP（6,448 与 17,360）在 203 GFLOP/s 下都是 0.05–0.1 µs 量级，**FLOP 不是瓶颈**。瓶颈是串行深度：Cholesky 之后的两次三角回代有 `2p = 64` 次长度 ≤ p 的归约，每次 5 级 `__shfl`、延迟 100–150 cycles，合计 4–6 µs，期间 63/64 的 warp 空转。GJ 每步 1024 个元素全并行，零归约。
**可推广的规则：当绝对 FLOP 已经降到 0.1 µs 量级时，选算法要看「串行深度 × 每步延迟」，不能看 FLOP。**

</details>

**Q2.** 为什么 Gram 的累加要「float 段内 + double 段间」，而不是直接全 double？

<details><summary>答案</summary>

全 double 的精度没问题，但 T4 的 FP64 是 FP32 的 **1/32** 速率。`p²n = 1e8` 次 DFMA 落到单个 SM 上是 31 ms，而这条路径的访存下界只有 1.6 ms（12.8 MB），等于把访存自由的 kernel 变成 FP64 受限。
分段把误差从 `ε√n`（3.8e-5）降到 `ε√C`（1.9e-6），而 double 加的次数只有 `n/C = 390` 次，代价可忽略。
**判据：要降低的只是「误差的增长阶」，不是「每一」次运算的精度。**

</details>

**Q3.** GJ 消元后为什么不把 `A[i][c]` 写回 0？它不写 0 会不会影响后面的计算？

<details><summary>答案</summary>

不影响，因为第 `c` 列在后续步骤里再也不被读（第 `c' > c` 步只碰 `j > c'` 的列）。写它反而有害：这一步里所有 `i != c` 的线程都要读 `A[i][c]` 当乘数，`(i,c)` 线程同时写 0 就在同一个 `__syncthreads()` 区间内构成竞争。
**这是「死数据」的一个用处：不写它就消灭了一个竞争面。**

</details>

**Q4.** 仿真通过了，能不能说明 CUDA 版本也能过？

<details><summary>答案</summary>

不能，只说明**索引和数值**对。仿真不覆盖：`__syncthreads()` 的位置是否正确（缺一个会读到未写完的 smem）、块内是否存在读写竞争、以及实际性能。
尤其 §6.3：最终版之所以能删掉 `__syncwarp()`，靠的是「第 `c` 步没有线程写 row `c`」这个论证。numpy 里没有竞争这回事，所以这个论证**完全靠代码审查**，仿真帮不上忙。

</details>

**Q5.** 拿到一个 `p = 32, n = 100000` 的测试用例，怎么在跑之前判断它会不会超容差？

<details><summary>答案</summary>

算 `κ(X) = σ_max/σ_min`，再看 `κ² × 1.2e-7`。`p=32, n=1e5` 的随机均匀矩阵 κ 约 1.4，判据给出 2.3e-7，远低于 1e-2，安全。
但如果 `X` 有近共线列，κ 会跳到 10³–10⁴，判据给出 1e-1～1e1，这时实测也确实是 0.55～1.3e+2（§7.3 表）。**预测和实测在同一量级，说明这个判据可以替代试跑。**

</details>
