# 10 · 调度、内存编排与 AOE（原 LayerGroup）

> 原课：LayerGroup 做算子调度与内存编排。  
> 昇腾：GE 内存/stream + **AOE** 自动调优。

---

## 1. LayerGroup 原课在解决什么（为什么）

片上内存装不下整网所有中间 tensor。必须：

- 把算子 **分组**  
- 组内复用 buffer  
- 决定计算顺序，让「死掉的」中间结果让出空间  

做不好 → 疯狂写 DDR → 变慢甚至编不过。

昇腾不强调同名模块，但 **问题同构**。

---

## 2. 概念模型（怎样工作）

```text
大图
  → 子图（按引擎/资源）
  → 组内：选顺序、分配/复用地址、插 DMA
  → 生成可执行 task 队列
```

| 机制 | 为什么 | 效果 |
|---|---|---|
| 内存复用 | 生命周期不重叠可共用地址 | 省片上/片外占用 |
| Stream | 多队列 | 搬运与计算重叠 |
| 融合 | 减少组边界上的写回 | 带宽↓ |

---

## 3. AOE——为什么还要自动调优

### 3.1 问题

切分、tile、算子实现组合爆炸；人肉搜不动，且随 shape/芯片变。

### 3.2 怎样工作

| 模式 | 搜什么 | 建议顺序 |
|---|---|---|
| **SGAT** 子图调优 | 切分策略 | **先做** |
| **OPAT** 算子调优 | 算子实现/参数 | 后做（基于最终 shape） |

可生成 **知识库**，下次 ATC 复用——类似「缓存下来的调优答案」。

### 3.3 效果与用在哪

效果：同一张图在目标芯片上更接近硬件甜点。  
用在哪：Profiling 显示仍慢、且图结构已相对干净之后（见 [13](./13-profiling.md)）。

---

## 4. 和原课 Auto-tuning / Kernel libraries 的连接

[02](./02-compiler-overview.md) Backend 的 Auto-tuning ≈ AOE。  
Kernel libraries ≈ 算子信息库里那些可选实现；OPAT 是在实现空间里搜。

## 5. 练习

1. 为何官方常建议先 SGAT 再 OPAT？  
2. 内存复用的前提「生命周期不重叠」用一句话解释。  
3. LayerGroup 与 GE 内存分配的类比。  
4. 什么时候不该一上来就 AOE？

### 参考答案

**1. 为何先 SGAT 再 OPAT？**

**SGAT** 搜的是 **子图怎么切**（图结构/边界变了，各子图看到的 shape、融合范围会变）。  
**OPAT** 搜的是 **某个算子用哪份实现/哪些参数**，依赖「最终落定的子图与 shape」。

若先 OPAT 再 SGAT：切分一变，刚才调好的算子场景可能作废，等于白搜。  
所以：**先定图怎么切（SGAT）→ 再在稳定 shape 下抠算子（OPAT）**。

**2. 「生命周期不重叠」一句话**

两个中间 tensor **不会在同一时刻都还「活着」**（一个已不再被后续 op 读，另一个才需要写），才可以 **共用同一块 buffer 地址**；若寿命相交，复用会互相踩数据。

**3. LayerGroup 与 GE 内存分配的类比**

**LayerGroup ≈ 原课里「把算子分组 + 组内排顺序 + 复用片上缓冲 + 必要时插搬运」的那套编排；GE 的内存/stream 规划 ≈ 昇腾上干同一类事：子图内分配与复用地址、用多 stream 让 DMA 与计算重叠，最终写进可执行 plan / om。**  
名字不同，问题同构：片上装不下整网 → 必须分组、复用、调度。

**4. 什么时候不该一上来就 AOE？**

AOE 贵、且假设「图大体正确、值得抠硬件甜点」。不该一上来就上的情况例如：

- **还没跑通**：Parser/精度/输入预处理都没过（先 ATC + msame）  
- **图还很脏**：冗余大、导出花活、明显能手改的结构问题没清  
- **Profiling 还没做**：不知道慢在访存还是算力、哪一段子图；盲搜性价比低  
- **契约未定**：shape/量化方案还在改，调优知识库容易马上过期  

建议顺序：正确性 → 简单图清理 → Profiling 定位 → **再** AOE（先 SGAT 后 OPAT）→ 必要时再 ATC。
