## 为什么现在讲这个

[33 章](./33-rdma-six-layer-spine.md) 对 Q11 只给了一句：`PSN + ACK/NAK + go-back-N`，
窗口里第 k 个包丢了，重传 `W-k+1` 个。
[38 章](./38-verbs-program-walkthrough.md) 又把 `timeout`/`rnr_retry` 当参数填进去了。
但三件事从来没算过：

1. 这个 `W-k+1` 到底是几个包？平均是几个？
2. **窗口开大一点难道不是更好吗？** —— 不是，而且坏处是定量的。
3. `timeout=14` 这个 67 ms 是拍脑袋还是算出来的？取小了会怎样？

这三个问题的答案凑在一起，会得出一个反直觉的结论：

> **丢包的主要代价不是重传的带宽，是等超时的时间。**

而 [35 章](./35-rdma-congestion-control-loop.md) 花那么大篇幅讲 PFC/DCQCN，
本质上是在给这一章的公式擦屁股：**只要你还在用 go-back-N，丢包就必须被消灭，
而不是被容忍。**

## 心智模型：窗口是"用带宽买延迟容忍"，go-back-N 是"用带宽买接收端内存"

RC 的可靠传输有两个独立的设计选择，很容易混成一个：

```text
选择 A：窗口大小 W
  决定"在途多少包" -> 决定能否填满 BDP -> 决定吞吐
  代价：丢包时要重发的量正比于 W

选择 B：出错后怎么重传
  选择性重传（SACK）：只重发丢的那个   -> 省带宽，但接收端要缓存乱序包
  go-back-N：从丢的那个开始全部重发   -> 省接收端内存，但费带宽
```

**RC 选的是 go-back-N。** 原因是 B 的取舍：

```text
选择性重传要求接收端能缓存 W x MTU 的乱序数据
  W=256, MTU=4KB  ->  1 MiB 接收缓冲，且每 QP 一份

VC/RC 的连接数动辄上千（34 章）->  这份缓存乘以 N，直接吃光 RQ 空间
```

所以 RC 的选择是：**接收端不缓存任何乱序包，全部丢弃**。
这换来了极简的接收端状态，代价是发送端必须回退重发。这就是 go-back-N 的来源，
也是为什么 Q11 的答案必须带"窗口"这个前提。

## 账本一：一次丢包的完整过程

脚本 [`42_psn_window_sim.py`](./42_psn_window_sim.py)：

```bash
cd ~/Downloads/learning_notes
python3 communication/42_psn_window_sim.py
```

`N=12, W=8, PSN 3 丢失` 的实际 trace：

```text
    轮次                    发送 PSN                                说明
     1  [0, 1, 2, 3, 4, 5, 6, 7]                      PSN 3 丢失
                       [0, 1, 2]  只收到这些，累积 ACK 停在丢失点
                    [4, 5, 6, 7]  乱序到达，被接收端丢弃（不缓存）
     2 [3, 4, 5, 6, 7, 8, 9, 10]            超时后重传整个窗口（go-back-N）
     3                      [11]            超时后重传整个窗口（go-back-N）

  重传的包：[3, 4, 5, 6, 7]
  重传数量 = W - k（k 是 0-indexed 的 PSN）= 8 - 3 = 5
  实际发出的包数 = 原始 12 + 重传 5 = 17
```

三个容易看漏的细节：

1. **ACK 是累积的**。收到 0,1,2 后回的是"我期望 3"，不是"我收到了 2"。
   所以丢包位置由 ACK 的期望值暴露，不需要单独 NAK。
2. **乱序包被丢弃，不是缓存**。`[4,5,6,7]` 白白浪费了一次传输——这是 go-back-N 的税。
3. **第 2 轮的窗口是 `[3..10]`，不是 `[8..15]`**。回退到丢失点重发，
   所以重发的是"从 3 开始的一个完整窗口"，其中 `8,9,10` 是本来没发过的新包。

### 公式与数法

```text
重传数 = W - k          （k 是 0-indexed 的 PSN）
重传数 = W - k + 1      （k 是「第 k 个」，1-indexed）
```

这两个式子差 1，**混用就会写错**。脚本做了穷举校验：

```text
    W    k      公式      实际重传
    8    0       8         8
    8    1       7         7
    8    4       4         4
    8    7       1         1
   16    0      16        16
   ...
  全部一致：是
```

平均代价（k 在 `0..W-1` 上均匀）：

```text
(1/W) * sum_{k=0}^{W-1} (W-k) = (W+1)/2
```

**每丢一个包，平均多烧 `(W+1)/2` 个包。** 这个数字直接把窗口大小和丢包率乘在了一起。

## 账本二：放大系数

```text
     W       p=0.01%       p=0.10%       p=1.00%       p=5.00%
     8         1.001         1.007         1.046         1.234
    32         1.003         1.023         1.178         2.032
    64         1.006         1.049         1.375         3.379
   128         1.006         1.084         1.771         6.459
   256         1.019         1.187         2.761        12.816
```

一阶近似是 `1 + p*(W+1)/2`，但仿真实测**偏大**，因为重传的包自己也会丢，误差会累积：

```text
p=1%,  W=256:  近似 1 + 0.01*128.5 = 2.285   实测 2.761
p=5%,  W=256:  近似 1 + 0.05*128.5 = 7.4     实测 12.816
```

### 这张表最反直觉的一格

`p=0.1%` 通常被认为"网络很干净"。但在 `W=256` 下：

```text
p=0.1%、W=256     放大 1.187     ！干净的网络也烧掉 19%
```

换算成带宽（400 Gbps）：

```text
     W     p=0.1% 有效     p=1% 有效     p=5% 有效
     8        398.1G      382.1G      319.4G
    32        394.0G      338.4G      191.2G
    64        387.3G      294.0G      114.6G
   128        374.5G      226.0G       59.1G
   256        361.5G      141.7G       29.7G
```

**`p=5%`、`W=256`：400G 的链路只剩 29.7G（不到 8%）。**

这时候现场会怎么做？查网卡、查 PCIe、换驱动、怀疑光模块。
全都查不到，因为网卡没问题——是丢包在吃带宽。而丢包的原因往往又是
[35 章](./35-rdma-congestion-control-loop.md) 的 PFC 没配好或 ECN 阈值不对。

这就是"**先扩窗口再扩不上去**"的机理：窗口越大，吞吐上限越高，
但每个丢包的成本也按 W 放大。两者在某一点交叉，加窗口不再有收益。

## 账本三：时间的代价其实在超时上

把放大系数换算成"一次丢包浪费多少时间"：

```text
浪费 ≈ ack_timeout  +  W x MTU / 带宽
```

`W=256, MTU=4KB, 400 Gbps`：

```text
W x MTU / 带宽 = 256 x 4096 B / 50 B/ns = 20,971 ns = 20.97 us
ack_timeout(14)                          = 67,108.9 us
占比：重传本身只占 0.03%
```

**丢包的延迟代价 99.97% 来自"等超时"，不是"重传数据"。**

这个结论有直接的操作含义：

```text
想降低丢包引起的尾延迟  -> 调 ack_timeout（且要保证不误判）
想降低丢包引起的带宽损失 -> 调窗口 / 降丢包率（PFC、ECN）
```

两件事要分开做。把 `timeout` 调到 `8`（1.05 ms）能把单次丢包的延迟惩罚从 67 ms
降到 1 ms——但前提是 RTT 加排队抖动不超过 1 ms，否则进入伪重传的死亡螺旋。

## 账本四：ack timeout 怎么选

`timeout` 是 5 bit 字段，语义是 `4.096 us × 2^value`：

```text
  value        超时(us)      超时(ms)   适用场景
      8        1048.6        1.05   同机架、无拥塞（约 1.05 ms）
     12       16777.2       16.78
     14       67108.9       67.11   跨机架常规值（约 67 ms）
     18     1073741.8     1073.74   广域/高抖动（约 1.07 s）
     20     4294967.3     4294.97   跨数据中心（约 4.3 s）
     31  8796093022.2  8796093.02

  0 表示无限等待（各实现处理不一，别依赖）
  字段只有 5 bit，最大 31 -> 8796.1 s
```

注意粒度的粗糙：**每一档是 2 倍**，你没法"微调"。
所以选值的原则是"覆盖最坏 RTT，且不超过 2 倍最优值"。

### 取小了：伪重传

```text
  value      超时(us)    超时/RTT                                后果
      3        32.8      0.27                每包都超时 -> 疯狂重传，带宽雪崩
      4        65.5      0.55                每包都超时 -> 疯狂重传，带宽雪崩
      5       131.1      1.09                       排队抖动一点就误判丢包
      6       262.1      2.18                        偏紧，适合低抖动环境
      8      1048.6      8.74                         安全，但故障发现慢
     14     67108.9    559.24                         安全，但故障发现慢
```

（RTT=120 µs）

`value=3` → 32.8 µs，比 RTT 还小。发送端的实际行为是：

```text
发一个包 -> 等 32.8us -> 没 ACK（ACK 还在路上）-> 重传
       -> 接收端收到重复包 -> 回重复 ACK
       -> 发送端看到"没进展" -> 再重传
```

现场表现是**"丢包率极高"**，但抓包会看到一个包都没丢。
这就是伪重传（spurious retransmit），也是 [36 章](./36-rdma-troubleshooting-decision-tree.md)
里 `RETRY_EXC_ERR` 和 `wc.status=SUCCESS 但延迟抖` 的常见成因。

**这类故障最坑的地方**：所有计数器都指向"网络丢包"，只有把 `timeout` 和实测 RTT
对照才能发现。

## 账本五：RNR 的等待上界

RNR（Receiver Not Ready）和超时是两套机制，但经常一起出错：

```text
RNR 表示「对端暂时没有 recv WR」
发送端按 rnr_retry 重试，每次等接收端设定的 min_rnr_timer

   rnr_retry                    行为           总等待(最坏)
          0              不重试，立即失败                 0
          1              重试 1 次           ~0.66 s
          3              重试 3 次           ~1.97 s
          6              重试 6 次           ~3.93 s
          7                  无限重试          永不报错（挂死）
```

（按最坏情况：接收端 `min_rnr_timer` 给到最长档 655.36 ms）

`rnr_retry=7` 的含义是"无限重试"，规范里 7 是特殊值。危险不在慢，在**永不失败**：

```text
对端 recv WR 永不投递  ->  发送端一直等  ->  应用 hang  ->  没有 wc.status
```

[38 章](./38-verbs-program-walkthrough.md) 的模拟器场景 C 复现的就是这个：
应用"hang 在等完成"，但拿到的其实是 RNR 错误——**前提是你设了有限值**。
设成 7 就连错误都拿不到。

## 常见错法，以及症状

| 错法 | 症状 |
| --- | --- |
| 窗口越大越好，一路调到 256 | 丢包率 0.1% 时白烧 19% 带宽；1% 时只剩 1/3 |
| 用 `W-k+1` 和 0-indexed PSN 混算 | 公式差 1，容量规划偏差一个包 |
| `timeout` 按"最优 RTT"设 | 伪重传：计数器显示大量重传，抓包一个都没丢 |
| `timeout` 按"最坏 RTT × 10"设 | 单次丢包延迟惩罚 67 ms，尾延迟爆炸 |
| `rnr_retry=7` 上生产 | 对端不投缓冲时永久挂起，不报错 |
| 把丢包当网卡故障查 | 换卡换驱动无效，因为根因是 `p × W` |
| 在丢包链路上加大窗口"提升吞吐" | 吞吐先升后降，交叉点由 `p` 决定 |
| 用 `p=0.1%` 论证"不需要 lossless" | 忽略 W：`W=256` 时这就是 19% 的税 |

倒数第一条特别值得记：**`p=0.1%` 是不是"干净"，取决于你的窗口大小**。
同样 0.1% 的丢包，`W=8` 是 0.7% 的税，`W=256` 是 18.7% 的税。
所以"这个网络够不够干净"这个问题，没有脱离窗口的答案。

## 模型边界

- 仿真是**包级离散模型**，一个"轮次"当作一个 RTT，没有建模 ACK 压缩与延迟 ACK
- 没有建模 NAK：真实 RC 在检测到 sequence error 时可能快速重传，不必等超时
  （这会让实际延迟低于模型的 67 ms，但放大系数不变）
- 没有建模 QP 级联：一个 QP 的 go-back-N 流量会加剧拥塞，进而增加丢包（正反馈）
- `ack_timeout` 只是**本地**超时，真实超时还要加对端的处理时间与排队
- RNR 的 timer 表按最坏档估算，实际值取决于接收端的 `min_rnr_timer` 设定
- 没有建模多路径（自适应路由会让同一 QP 的包乱序，触发伪丢包，见 Q25）

最后一条值得强调：**乱序会被误判成丢包。** go-back-N 只认"累积 ACK 的期望值"，
如果包走了不同路径导致乱序到达，接收端一样会丢弃并触发重传——
这不是丢包，但代价与丢包完全相同。所以自适应路由和 go-back-N 天生冲突，
这也是 [35 章](./35-rdma-congestion-control-loop.md) 里路由策略要谨慎的原因。

<details>
<summary>答案</summary>

1. `W - k = 256 - 200 = 56` 个（0-indexed）。若按"第 k 个"（1-indexed）数是 `W-k+1`。
   两种数法差 1，混用就错。
2. `k` 在 `0..W-1` 均匀时，`W-k` 的均值是 `W - (W-1)/2 = (W+1)/2`。
   含义：每丢一个包，平均多烧半个窗口。
3. **不能脱离窗口回答。** `W=8` 时是 0.7% 的税，`W=256` 时是 18.7% 的税。
   "干净"必须相对于窗口大小和你能接受的带宽损失。
4. 约 **141.7 Gbps**（放大 2.761 倍）。现场查不到是因为网卡/PCIe/驱动都正常，
   根因是 `p × W` 的乘积，不在任何单点计数器上。
5. 主要来自**等超时**：`ack_timeout(14) = 67,108.9 µs`；
   重传本身的传输时间 `256 × 4096 / 50 B/ns = 20.97 µs`，只占 0.03%。
6. 伪重传。超时小于真实 RTT，每包都在 ACK 回来之前被重传，
   现场表现为"丢包率极高"，但抓包一个包都没丢。
7. 因为选择性重传要求接收端缓存最多 `W × MTU` 的乱序数据，每 QP 一份。
   RC 的连接数上千（[34 章](./34-rdma-connection-state-ledger.md) 的状态账本），
   这份缓存乘以 N 会吃光 RQ 空间。所以 RC 选择丢弃乱序包、换取极简接收端状态。
8. 因为 go-back-N 只认累积 ACK 的期望值。多路径导致包乱序到达时，
   接收端一样丢弃乱序包并触发重传——代价与真丢包完全相同，
   自适应路由的负载均衡收益被重传吃掉了。

## 一页速记

```text
两个独立选择:
  W（窗口）      决定吞吐上限，也决定丢包代价
  重传方式       go-back-N（RC）：不缓存乱序，省接收端内存

重传数:
  W - k        （k 是 0-indexed PSN）
  W - k + 1    （k 是「第 k 个」，1-indexed）   混用差 1
  平均 (W+1)/2  <- 每丢一包多烧半个窗口

放大与吞吐（400G）:
  W=256 p=0.1%  -> 放大 1.187 -> 361.5G
  W=256 p=1%    -> 放大 2.761 -> 141.7G
  W=256 p=5%    -> 放大 12.816 -> 29.7G
  近似 1 + p*(W+1)/2，实测更大（重传自己也会丢）

时间代价:
  ≈ ack_timeout + W*MTU/带宽
  W=256, MTU=4K, 400G, timeout=14:
    67,108.9 us (超时)  vs  20.97 us (重传)   -> 99.97% 在等超时

ack_timeout = 4.096us * 2^value（5 bit，每档 2 倍）
  8 -> 1.05ms   14 -> 67.11ms   18 -> 1.07s   31 -> 8796s
  取小 -> 伪重传（显示大量丢包，实际零丢包）
  取大 -> 单次丢包延迟惩罚线性放大

RNR:
  rnr_retry=7 是无限重试 -> 永不失败 -> 应用 hang 但没有 wc.status
  生产用有限值，让故障暴露

结论:
  丢包必须被消灭（PFC/DCQCN），不能被容忍
  乱序 = 假丢包，所以自适应路由与 go-back-N 天生冲突
```
