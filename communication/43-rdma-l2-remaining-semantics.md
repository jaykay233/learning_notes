# L2 剩余语义：MTU、inline、immediate、atomic、UD 各自在买什么

知识点：MTU 决定瓶颈从带宽变 pps、inline 省哪一次访问、imm 的信令语义、atomic 的边界、UD 的取舍
上次：L3 可靠性定量（42）——窗口与超时怎么算
下次：44 · 流控与背压（WRITE 的"零背压"到底意味着什么）

## 为什么现在讲这个

[33 章](./33-rdma-six-layer-spine.md) 的 L2 只画了一张四方象表（SEND / WRITE / WRITE_WITH_IMM / READ+ATOMIC），
剩下六个问题——MTU、inline、immediate、fence、atomic、UD——被压成了几句要点。
它们看起来是"实现细节"，但每一个都在买一个具体的东西：

```text
MTU        买「包数少」      代价：大包增加单包延迟与丢包代价（42 章）
inline     买「少一次回读」  代价：WQE 空间，且数据不能被远端 READ
immediate  买「一次内存读」  代价：占一个 recv WR
atomic     买「一次往返」    代价：只有 8 字节，单地址串行
UD         买「无连接状态」  代价：不可靠、消息 ≤ MTU
fence      买「跨 QP 顺序」  代价：一条流水线屏障
```

**这一章的做法是：每个机制给出"它省掉哪一次具体操作"，然后算这笔账。**
因为面试里最容易被追问的就是"inline 到底省了什么"——答"省了一次拷贝"是错的。

## 心智模型：每个语义选择都在"用资源换资源"

把这六个机制放在一张资产负债表上，规律立刻显出来：

```text
机制        买到的              付出的
MTU 4K      瓶颈留在带宽侧      单包延迟↑、丢包代价↑（42 章）
inline      少一次 PCIe 回读    WQE 变胖、队列深度↓、不可远端 READ
immediate   消掉可见性竞态      占一个 recv WR、只有 32 bit
atomic      少一次往返          只能 8 字节、单地址串行
UD          无连接状态（O(1)）  不可靠、消息 ≤ MTU
fence       跨操作可见性        一条流水线屏障
```

**没有一项是单向变好。** 所以判断"该不该用"的正确问法是：

```text
这个机制省掉的资源，是不是我当前的瓶颈？
它付出的资源，我是不是富余？
```

举例：`inline` 在延迟敏感的 RPC 上值得（延迟是瓶颈，WQE 空间富余）；
在吞吐优先的大块传输上不值得（WQE 深度是瓶颈，延迟不是）。

## 一、MTU：瓶颈会从"带宽"换成"pps"

大多数人以为 MTU 影响的是"头部浪费几个字节"。真实的机制是**两个独立资源**：

```text
总时间 = max( 线上字节数 / 带宽,  包数 × 每包处理时间 )
         └── 字节受限 ──┘        └── 包率受限 ──┘
```

它们是**取 max 而不是相加**——因为 DMA 和链路是并行工作的。
但当包变小，`包数 × 每包处理` 会超过 `字节数 / 带宽`，瓶颈就换了。

脚本 [`43_l2_semantics_cost.py`](./43_l2_semantics_cost.py)（1 MiB 消息，400 Gbps）：

```text
     MTU      包数      头开销     字节 ns     包处理 ns      瓶颈    有效 Gbps      效率
     256    4096   24.3%     27689     327680     包处理       25.6    6.4%
     512    2048   13.8%     24330     163840     包处理       51.2   12.8%
    1024    1024    7.4%     22651      81920     包处理      102.4   25.6%
    2048     512    3.8%     21811      40960     包处理      204.8   51.2%
    4096     256    2.0%     21391      20480      带宽      392.1   98.0%
```

**MTU 从 4K 降到 256，有效带宽从 392 Gbps 掉到 25.6 Gbps，差 15 倍。**

而"头开销"那一列只从 2.0% 涨到 24.3%——单看头部，你会以为只损失 22%。
真正的杀手是**包处理**：`4096 包 × 80 ns = 327,680 ns`，是字节时间的 11.8 倍。

### 三个直接推论

1. **"MTU 设大一点"不是优化，是换资源**。大包把压力从 pps 转到带宽，
   而带宽通常更充裕。
2. **`path_mtu` 必须两端一致**。一端 256 一端 4K 时协商会失败或取小值，
   然后你就在 25.6 Gbps 那条曲线上，所有调参都无效。
3. **小 MTU + 大消息 = 双重惩罚**。[42 章](./42-rdma-reliability-psn-window.md) 的放大系数是按"包"算的：
   MTU 减半，包数翻倍，丢一个包的代价也随之变化（窗口是按包计的）。

这也解释了 Q16 为什么常选 4K：不是"4K 比较整"，而是**它是把瓶颈留在带宽侧的最小值**。

## 二、inline：省的是 NIC 回读 payload 的那一次 PCIe 访问

先纠正一个常见错误答案："inline 省了一次内存拷贝"。**不是。**

```text
非 inline（SGE）:
  WQE 里放 SGE{addr, len, lkey}
  -> NIC 读 WQE
  -> NIC 再用 lkey 做地址翻译，通过 PCIe 回读 payload
  -> 组包上链

inline:
  WQE 里直接跟着 payload
  -> NIC 读 WQE 时 payload 一起到手
  -> 组包上链
```

省掉的是**中间那次 PCIe 回读 + 地址翻译**。脚本按 250 ns 算：

```text
      消息    inline   非 inline ns   inline ns        省下(占端到端)
      32         是        1750.6      1500.6          14.3%
      64         是        1751.3      1501.3          14.3%
     128         是        1752.6      1502.6          14.3%
     256         是        1755.1      1505.1          14.2%
     512         否        1760.2           —               —
    1024         否        1770.5           —               —
```

（分母含 [33 章](./33-rdma-six-layer-spine.md) 的 1500 ns 固定成本）

**256 B 以内省约 14%，绝对值 250 ns。** 对吞吐几乎无影响，对延迟敏感的 RPC 可观。

两个必须记住的边界：

```text
1) 有上限：max_inline_data（常见 256 B）。超了必须走 SGE。
2) inline 的数据不能被远端 READ —— 它不在可翻译的内存里，只存在于 WQE。
```

第 2 条经常被踩：为了省延迟把请求改成 inline，结果对端用 READ 来取数据，直接失败。

## 三、immediate：32 bit 带外信令，省的是接收端一次内存读

对比两种"写完了通知你"的做法：

```text
WRITE + 轮询 flag:
  发送端把 flag 写在数据区约定位置
  接收端 spin 读那个 flag  <- 每次都是一次本地内存访问
  问题：flag 与数据不在同一原子单位里，可能读到「flag 已置、数据未到」

WRITE_WITH_IMM:
  发送端 WRITE 数据 + 32 bit imm
  接收端拿到一个 RECV CQE，imm 在 wc.imm_data  <- 不碰数据区
```

脚本的账（一次轮询 80 ns，平均 3 次命中）：

```text
                    方案        接收端额外成本   说明
       WRITE + 轮询 flag                240 ns   依赖数据可见性，易读到半新半旧
        WRITE_WITH_IMM     0（复用 poll）   需要一个 recv WR 承接
```

**imm 的真正价值不是"省 240 ns"，是消除"flag 与数据可见性不一致"这个竞态。**
轮询方案在 [42 章](./42-rdma-reliability-psn-window.md) 的乱序/重传下会出现
"flag 到了但数据还在重传"，这是很难复现的 bug。

三条约束：

```text
1) 接收端必须预投 recv WR，否则 RNR（42 章）
2) imm 只有 32 bit，装不下指针；常见用途是「序号 / slot id / 消息类型」
3) 同 QP 内 imm 的到达顺序有序；跨 QP 无序（要 fence）
```

## 四、atomic：省的是"一次往返"，不是"算得快"

```text
READ + 本地算 + WRITE:   2 次往返，6000 ns（RTT 3000 各一次）
ATOMIC fetch_and_add:    1 次往返，3120 ns（RTT + NIC 内部 120 ns）

省下 1.9x
```

关键在于：**这 1.9x 全部来自少一次往返，和计算无关。**
所以 atomic 只对"简单运算 + 高频"有价值：

```text
适合：计数器、配额扣减、序号分配、CAS 锁
不适合：需要读多个字段再判断的复杂逻辑（它做不到）
```

### 四条硬限制（Q15 的答案）

```text
· 只有 8 字节（32/64 bit）。没有通用的 128 bit atomic。
· MR 要有 REMOTE_ATOMIC 权限，地址要 8 字节对齐。
· 同一地址上的 atomic 在 NIC 内串行化 -> 热点地址直接变成瓶颈。
· 只是单地址原子性，不是事务。跨对象的「一起改」它不保证。
```

第三条最容易被低估。一个全局计数器被 128 个 QP 同时 `fetch_and_add`，
每次串行 → 吞吐上限就是 `1 / 单次 atomic 时长`，与你有多少 QP 无关。
这时正确做法是**分片**（每个 QP 加到自己那片，最后汇总），不是加 QP。

## 五、UD：用"不可靠"换"无连接状态"

[34 章](./34-rdma-connection-state-ledger.md) 已经算过连接状态的账。
UD 的定位就是把这个账**彻底消掉**：

```text
                    场景              RC                UD   原因
                  对端数量         O(N) 状态           O(1) 状态   UD 不需要建连
                 单消息上限            几乎无限       <= path MTU   UD 一条消息一个包
             消息大小 64 B        1.5 us 级          1.5 us 级   都是单包，固定成本主导
             消息大小 1 MB            一条消息               做不到   UD 超过 MTU 无法发送
                   可靠性            硬件重传                 无   UD 丢了就丢了
                    顺序         同 QP 有序               不保证   多路径/多包无序号
```

**UD 的适用边界是「小消息 + 海量对端」：**

```text
N = 10000 个对端
  RC: 10000 条连接 -> 34 章的账本撑不住（每条约 512 B 上下文 + RQ + MTT）
  UD: 几条 QP 就够 —— 每个包自带 GRH（目标地址），无状态
```

代价是每个包都要带 GRH（额外几十字节），且**一条消息不能超过 MTU**。
所以 UD 只能送"够小的东西"：服务发现、心跳、元数据、控制面。

这就是 Q17 的完整答案：UD 不可靠却重要，因为**它是唯一能规模化的无状态模式**。
不是因为"UD 更快"——单包延迟和 RC 差不多。

## 六、fence：只在需要时才付这条流水线屏障

```text
RDMA READ 完成  ->  数据在本地内存可见
后续的 SEND/WRITE 是否一定看到这份数据？  不一定 —— 除非加 IBV_SEND_FENCE
```

fence 的语义很窄：

```text
保证：同一个 QP 上，fence 之前发出的 RDMA READ 已完成，且数据对后续操作可见
不保证：跨 QP 的顺序（那是另一个 QP 的事，要自己做同步）
不保证：本地 CPU 的缓存一致性（那是 CPU barrier 的事）
```

所以 Q14 的答案是：**同一个 QP 内天然有序；跨 QP 无序，必须自己建同步点。**
`IBV_SEND_FENCE` 只解决"读后写"这一个模式，不是万能锁。

## 常见错法，以及症状

| 错法 | 症状 |
| --- | --- |
| 以为 MTU 只影响头部开销 | 小 MTU 下带宽只有 1/15，却查不到原因 |
| 两端 `path_mtu` 不一致 | 协商失败或取小值，然后是上一条 |
| 为了省延迟把请求改 inline | 对端用 READ 取数据直接失败（inline 数据不可远端读） |
| inline 设很大 | WQE 变胖、队列深度变浅，吞吐反而下降 |
| 用 WRITE + 轮询 flag 做通知 | 偶发读到"flag 已置、数据未到" |
| 用 atomic 做复杂逻辑 | 只能 8 字节单地址，写不出来只能退化成一串 atomic，反而更慢 |
| 热点地址上用 atomic 做全局计数 | 吞吐被串行化锁死，加 QP 无效 |
| 以为 UD 更快 | 单包延迟与 RC 相同；UD 换来的是无状态，不是速度 |
| 用 UD 传大消息 | 超过 MTU 直接发不出去 |
| 以为 fence 能保证跨 QP 顺序 | 依然乱序，偶发数据竞争 |

第 7 条和第 4 条是同一类错误：**把"资源换资源"当成"免费优化"**。
RDMA 的每个机制都是在两个资源之间换，没有单向的变好。

## 模型边界

- `PKT_PROCESS_NS = 80`（12.5 Mpps）是**假设的网卡能力**，不同代差很大；
  但"小 MTU 时瓶颈换成 pps"这个结构性结论不随具体值改变
- 每包开销按 RoCEv2 的 82 B 算；加 VLAN/隧道会更多
- inline 的 250 ns 是 PCIe 回读的量级，实际取决于 PCIe 代宽与 IOMMU
- atomic 的 120 ns 是 NIC 内部执行，实际热点场景还要加排队
- 没有建模 WQE 缓存命中率，而它对 inline 的收益影响很大
- UD 的 GRH 开销没有计入带宽，实际会占几个百分点

## 自测

1. MTU 从 4K 降到 256，为什么有效带宽会掉 15 倍？瓶颈从什么换成了什么？
2. inline 省的到底是哪一次操作？为什么它不能被远端 READ？
3. `WRITE + 轮询 flag` 和 `WRITE_WITH_IMM` 的真正差别是延迟还是正确性？
4. atomic 省下 1.9 倍，这 1.9 倍来自哪里？它为什么不能做事务？
5. 一个全局计数器被 128 个 QP 同时 atomic，为什么加 QP 没用？
6. UD 的适用边界是什么？为什么它不是"更快的 RC"？
7. `IBV_SEND_FENCE` 保证什么、不保证什么？

<details>
<summary>答案</summary>

1. 因为总时间是 `max(字节时间, 包数 × 每包处理)`。4K 时字节时间是瓶颈（98% 效率），
   256B 时包数变成 4096，`4096 × 80 ns` 是字节时间的 11.8 倍，
   **瓶颈从 B/ns 换成了 pps**（网卡硬上限）。
2. 省的是 NIC 通过 PCIe **回读 payload 并做地址翻译**的那一次访问（约 250 ns）。
   inline 的 payload 只存在于 WQE 里，不在可翻译的内存地址空间中，
   所以远端 READ 找不到它——这是硬约束，不是实现缺陷。
3. **正确性为主。** 延迟上 imm 省的是 240 ns 级；真正的价值是消除
   "flag 已置但数据未到"的竞态（在乱序/重传下尤其明显）。
4. 来自**少一次往返**（2 次 RTT → 1 次）。和计算速度无关。
   不能做事务，因为它只保证**单个 8 字节地址**的原子性，
   跨多个对象的"一起改"它没有语义支持。
5. 因为同一地址上的 atomic 在 NIC 内**串行化**。吞吐上限是 `1 / 单次 atomic 时长`，
   与 QP 数无关。正确做法是分片计数再汇总。
6. 边界是"小消息 + 海量对端"：消息 ≤ MTU、无连接状态、不保证送达。
   单包延迟与 RC 相同，UD 换来的是**可规模化**（O(1) 状态），不是速度。
7. 保证**同一个 QP 上** fence 之前的 RDMA READ 已完成且数据对后续操作可见。
   不保证跨 QP 顺序，也不保证 CPU 缓存一致性。

</details>

## 一页速记

```text
MTU:  总时间 = max(字节/带宽, 包数 x 每包处理)     <- 取 max，不相加
      4K -> 392G (98%)   1K -> 102G   256B -> 25.6G (6.4%)
      小 MTU 的瓶颈是 pps，不是头部开销
      path_mtu 两端必须一致

inline: 省 NIC 回读 payload 的 PCIe 访问（~250 ns，256B 内省 14%）
        上限 max_inline_data；inline 数据不能被远端 READ
        代价：WQE 变胖、队列深度变浅

imm:   32 bit 带外信令，省接收端一次内存读（~240 ns）
       真正价值：消除 flag 与数据的可见性竞态
       约束：需预投 recv WR；装不下指针；跨 QP 无序

atomic: 省一次往返（2 RTT -> 1 RTT，1.9x），不是算得快
        只有 8 字节 / REMOTE_ATOMIC / 8 字节对齐
        同地址串行化 -> 热点头用分片，不要加 QP
        单地址原子性 != 事务

UD:     换的是无连接状态（O(1) vs O(N)），不是速度
        消息 <= MTU；不可靠；不保证顺序
        适用：小消息 + 海量对端（发现、心跳、控制面）

fence:  只保证同 QP 内「READ 完成 -> 后续操作可见」
        跨 QP 顺序必须自己同步

一句话: 每个机制都在拿一个资源换另一个，没有单向变好
```
