## 为什么现在讲这个

[33 章](./33-rdma-six-layer-spine.md) 已经把三个公式写出来了：

```text
① 延迟 = 固定成本 + 线上时间      ≈ 1.5 us + size*8/带宽
② 单 QP 消息率 = 1 / (固定成本 + 线上时间)
③ Little's law：在途条数 = 消息率 x RTT
```

但公式写在纸上和"能在面试/排障里用"是两件事。三个具体的困难：

```text
1) 知道公式，但不知道自己系统的「固定成本」是多少 -> 算不出任何数
2) 知道 Little's law，但不知道它反过来的用法 -> 诊断不出「深度不足」
3) 知道四个因素都影响带宽，但不知道「该先查哪一个」-> 排障顺序错
```

这一章解决这三件事：给出一份可改参数的**成本分解**、
一个把 Little's law **反用**的容量公式、以及一张**四种瓶颈的判定表**。

最重要的一个公式是反用的那条：

```text
可达带宽 = 在途条数 x 消息大小 / RTT
```

它解释了生产里最常见的困惑：**链路是 400G，但只有 50G 在跑，而且没有任何错误。**

## 心智模型：四个上限，取最小的那个

任何时刻，你实际能跑到的带宽是下面四个数的**最小值**：

```text
线速        = 链路带宽                        （硬件）
固定成本    = size / (固定成本 + 线上时间)      （每消息开销）
在途深度    = 深度 x 条数 x size / RTT          （Little's law）
网卡消息率  = 150 M msg/s x size                （CQ/PCIe 处理能力）
```

这个模型的价值在于**排障顺序**。绝大多数"带宽上不去"根本没走到"查链路"那一步：

```text
小消息 + 单 QP     -> 固定成本（最常见，1 KB 只有 5.4G）
中等消息 + 浅队列   -> 在途深度
小包 + 很多 QP     -> 网卡消息率
大消息 + 大队列     -> 才轮到线速/PCIe/PFC
```

**先算，再查。** 一张纸能算出来的东西，不要先去抓包。

```text
      消息大小     100G 效率     200G 效率     400G 效率     400G 有效        消息率
      64 B       0.3%       0.2%       0.1%        0.3G      0.67M
     256 B       1.3%       0.7%       0.3%        1.4G      0.66M
      1 KB       5.2%       2.7%       1.3%        5.4G      0.66M
      4 KB      17.9%       9.8%       5.2%       20.7G      0.63M
     16 KB      46.6%      30.4%      17.9%       71.7G      0.55M
     64 KB      77.8%      63.6%      46.6%      186.5G      0.36M
      1 MB      98.2%      96.5%      93.3%      373.3G      0.04M
```

（固定成本 1500 ns，效率 = 线上时间 / (固定成本 + 线上时间)）

三个必须记住的读法：

1. **1 KB @ 100G 只有 5.2%** —— 这和 33 章的 81.9 ns / 1582 ns 完全一致。
   "100G 网卡跑小消息只有几 Gbps"不是硬件坏了。
2. **同样的 1 KB，400G 的效率反而更低（1.3% vs 5.2%）**：
   带宽涨 4 倍，固定成本一分没少。**链路越快，小消息越浪费。**
3. **消息率那一列几乎不动（0.67M → 0.66M → 0.63M）**：
   小消息下"每秒能发多少条"由固定成本决定，与带宽无关。

第 2 条是一个反直觉但非常有用的结论：升级到 400G 之后，
如果你的工作负载还是 1 KB 小消息，**有效吞吐只从 5.4G 涨到 5.4G**——一分没涨。

## 固定成本到底花在哪

```text
                       段      介质      ns      占比
              填 WQE（用户态）     CPU     350  23.3%
        doorbell（MMIO 写）    PCIe     150  10.0%
         网卡取 WQE（PCIe 读）    PCIe     250  16.7%
           对端写内存（PCIe 写）    PCIe     300  20.0%
        产 CQE + 用户态 poll     CPU     450  30.0%
                      合计            1500 100.0%
```

**三段在 PCIe 上，合计 700 ns = 47%。**

这解释了两件事：

- 为什么 [37 章](./37-rdma-gpudirect-degradation.md) 的 GPUDirect 值得做——
  它把"对端写内存"这一段从"写 host 内存再拷贝到显存"变成"直接写显存"；
- 为什么 [43 章](./43-rdma-l2-remaining-semantics.md) 的 inline 有效——
  它砍掉的是"网卡取完 WQE 之后还要再读一次 payload"这次 PCIe 访问（账单上 250 ns 里的那部分）。

**换自己的系统时，把这张表按实际测量替换掉即可。** 五段的结构不会变。

## Q37：想提高消息率，三种手段各值多少

```text
   基准：1 KB @ 100G，固定成本 1500 ns -> 0.632 M msg/s
   目标：打满 100G 需要 12.21 M msg/s

                        手段      固定成本 ns      msg/s      相对提升      需要多少 QP
              基线（每消息一个 WR）       1500.0     0.632M     1.00x         19.3
  inline（省 WQE 回读 payload）       1250.0     0.751M     1.19x         16.3
doorbell batching x16（摊销 150）       1359.4     0.694M     1.10x         17.6
     CQ moderation（摊销 450）       1078.1     0.862M     1.36x         14.2
       inline + 双 batching        687.5     1.300M     2.06x          9.4
```

四条读法：

- **inline 砍 250 ns，提 19%**，但它依赖 payload，大消息无效
  （[43 章](./43-rdma-l2-remaining-semantics.md)：inline 有长度上限）
- **只摊销 doorbell 只提 10%** —— 150 ns 本来就不是大头。
  这是个常见的错误优化方向。
- **摊销 CQE（CQ moderation）提 36%**，因为它占固定成本的 30%，
  是单项最大的一块。
- **三者叠加 2.06x**，但代价是延迟变差（等批满、等中断合并）。

最重要的一行是最后一列的 9.4：

> **即使把固定成本压掉一半，打满 100G 仍需约 10 个 QP。**

因为"单 QP 有上限"这件事没有被改变，只是上限被抬高了。
所以 Q37 的标准答案是**两层**：先压固定成本，再上多 QP。只做一层都不够。

## Q38：延迟下限怎么拆

```text
   1 KB @ 100G，RTT 2 us（传播按 RTT/2 计）

                         项        ns      占端到端
                填 WQE（用户态）     350.0    13.6%
          doorbell（MMIO 写）     150.0     5.8%
           网卡取 WQE（PCIe 读）     250.0     9.7%
             对端写内存（PCIe 写）     300.0    11.6%
          产 CQE + 用户态 poll     450.0    17.4%
                线上传输（1 KB）      81.9     3.2%
           传播 + 交换机（RTT/2）    1000.0    38.7%
                        合计    2581.9   100.0%
```

三条可操作结论：

1. **固定成本 1500 ns 占 58%，线上只有 82 ns（3.2%）**。
   所以降延迟的第一优先级是压固定成本，不是换更快的网卡。
   换 400G 只能把 82 ns 变成 20 ns，总延迟从 2.58 us 降到 2.52 us —— **2.4%**。
2. **传播占 39%，是第二大项**。跨机架多 2 us RTT 会再吃掉 ~40%，
   这就是"同机架优先"的量化理由。
3. 接收侧 450 ns + doorbell 150 ns 可以用 busy polling 与 batching 压掉一部分，
   代价是一个核（[45 章](./45-rdma-vs-dpdk-and-routing.md) 算过核的价钱）。

### Q38 的正确答法结构

面试里问"怎么把延迟做到最低"，不要罗列清单，按**占比**回答：

```text
固定成本 58%  -> 先压这里：inline、batching、预注册、busy poll
传播     39%  -> 拓扑：同机架、少跳数、扁平网络
线上      3%   -> 换网卡，收益最小
```

"换更快的网卡"排在最后，这一点几乎是所有初学者的答案。

## Q39：深度设小了会发生什么

```text
    深度      1 KB      4 KB     64 KB        打满 400G 所需深度
    16     26.2G    104.9G    400.0G           1KB 需 245
    64    104.9G    400.0G    400.0G           1KB 需 245
   128    209.7G    400.0G    400.0G           1KB 需 245
   256    400.0G    400.0G    400.0G                   —
   512    400.0G    400.0G    400.0G                   —
  1024    400.0G    400.0G    400.0G                   —
```

（400G 链路，RTT 5 us）

读法：

- 深度 128 时 1 KB 只能跑到约 **210G** —— 链路是 400G，一半带宽用不上。
- 而且**没有任何错误**：`wc.status` 全 `IBV_WC_SUCCESS`，计数器全干净，只是速率上不去。

**这是最容易被误判成"网络问题"的一类现象。**
它连 [36 章](./36-rdma-troubleshooting-decision-tree.md) 的判定树都走不进去——
因为判定树的前提是"有异常证据"，而这里什么证据都没有。

### 需要多少深度

```text
     链路   RTT us    BDP KB     1KB 所需      x2      x4      超过默认 128?
   100G      2.0      24.4       24.4      49      98              否
   200G      5.0     122.1      122.1     244     488              是
   400G      5.0     244.1      244.1     488     977              是
   400G     20.0     976.6      976.6    1953    3906              是
```

400G / RTT 20 us（跨机房）需要 **2000 个在途**。
这不是"调一个参数"能解决的——必须改架构（DC / 多 QP / 流水线）。

## 综合：先算再查

```text
                                场景        可达      占比   瓶颈
      1 KB, depth128, 1QP, RTT 5us      5.4G     1%   固定成本
       4 KB, depth8, 1QP, RTT 20us     13.1G     3%   在途深度
             64 B, depth512, 512QP     76.8G    19%   网卡消息率
     64 KB, depth256, 2QP, RTT 5us    373.1G    93%   固定成本
      16 MB, depth64, 1QP, RTT 5us    398.2G   100%   线速
```

这张表就是排障时的检查顺序：

```text
「1 KB 单 QP 只有 5.4G」            -> 固定成本，物理天花板
「4 KB / depth 8 / RTT 20us 只有 13.1G」-> 在途深度不足
「64 B 加到 512 QP 也只有 76.8G」     -> 网卡消息率上限
「16 MB 才摸到线速」                 -> 只有大消息才轮到链路当瓶颈
```

**注意：前四种情况你都还没走到"查链路"那一步。**

## 常见错法，以及症状

| 错法 | 症状 |
| --- | --- |
| 用小消息压测就判断"网卡不行" | 5% 效率是物理规律，不是故障 |
| 升级到 400G 但工作负载是 1 KB | 有效带宽几乎没变，误判为"没生效" |
| 优先优化 doorbell | 只提 10%，因为 150 ns 不是大头 |
| 只压固定成本不上多 QP | 最多 2x，仍到不了线速 |
| 只上多 QP 不压固定成本 | QP 数线性涨，CPU 与表项跟着涨 |
| 深度设成默认 128 就跑 400G | 1 KB 卡在 210G，无任何错误 |
| 把"深度不足"当丢包查 | 计数器全干净，查不出任何东西 |
| 降延迟先换网卡 | 线上只占 3%，收益 2.4% |
| 忘记 RTT 里的传播项 | 跨机架场景算出的深度差 4 倍 |

倒数第二条值得展开：**换 100G→400G 把线上时间从 82 ns 降到 20 ns，
总延迟从 2.58 us 降到 2.52 us。** 花 4 倍带宽的钱买 2.4% 的延迟。

## 模型边界

- 五段固定成本的绝对值是量级假设（350/150/250/300/450 ns）；
  真实值随 CPU、PCIe 代际、厂商实现变化，但**结构（PCIe 占近半）稳定**
- 固定成本按"每消息"计；真实实现里 WR 批处理会让它随批大小变化
- 传播按 RTT/2 计，忽略交换机排队；拥塞时这一项会显著上升
- 没有建模流水线重叠：连续消息的固定成本可以部分重叠，
  所以**稳态吞吐**比"单消息延迟的倒数"高，但**单条延迟**仍按本表
- 网卡消息率上限 150 M msg/s 是假设值，不同代差很大
- 没有建模 PCIe 带宽竞争（多 QP 共享 PCIe 时会互相挤）

最后一条边界值得强调：**本表算的是"单条消息的延迟"和"稳态吞吐上限"两件事，
不要混用。** 延迟按本表逐段相加；吞吐要用 Little's law 反推。

## 自测

1. 1 KB 消息 @ 400G 的有效带宽是多少？为什么比 @ 100G 还低？
2. 固定成本 1500 ns 里，PCIe 占多少？这解释了什么优化为什么有效？
3. inline / doorbell batching / CQ moderation 各提多少？哪个最不值？
4. 为什么"压掉一半固定成本"仍打不满 100G？
5. 1 KB @ 100G RTT 2us，端到端延迟大约多少？各项占比如何？换 400G 能省多少？
6. 400G、RTT 5us、1 KB 消息，深度 128 能跑多少？为什么没有报错？
7. 给出"可达带宽"的反推公式，并说明它对应 Little's law 的哪种用法。
8. 带宽上不去，排障的四个上限按什么顺序查？为什么最后才查链路？

<details>
<summary>答案</summary>

1. **5.4 Gbps（1.3%）**。因为 400G 下线上时间只有 20.5 ns，
   而固定成本仍是 1500 ns；效率 = 20.5/1520.5 = 1.3%。
   100G 时线上 81.9 ns，效率 5.2%。**带宽越高，固定成本占比越大，所以越浪费。**
2. **700 ns，47%**（doorbell 150 + 取 WQE 250 + 对端写内存 300）。
   它解释了 GPUDirect（把写内存那段变成直写显存）与
   inline（砍掉取 WQE 后再读 payload）为什么有效。
3. inline 1.19x、doorbell batching 1.10x、CQ moderation 1.36x，叠加 2.06x。
   **doorbell batching 最不值**——150 ns 只占固定成本 10%。
4. 因为"单 QP 有上限"这件事没有被改变，只是上限抬高。
   压掉一半后仍需约 10 个 QP 才能打满 100G（1 KB）。所以必须两层一起做。
5. 约 **2.58 us**：固定 1500 ns（58%）、传播 1000 ns（39%）、线上 82 ns（3.2%）。
   换 400G 只把线上降到 20 ns，**总延迟降 2.4%**——所以换网卡是最后手段。
6. **约 210 Gbps**（`128 × 1024 × 8 / 5us`）。
   没有报错是因为没有丢包、没有重传、CPU 也没被打满——
   只是"在途条数不够"，Little's law 决定的上限，网卡和协议层都不知道这件事。
7. **可达带宽 = 在途条数 × 消息大小 / RTT**。
   它是 Little's law（在途 = 速率 × RTT）的逆用，用来做容量规划，
   而正用（由速率推深度）用来做参数配置。
8. 固定成本 → 在途深度 → 网卡消息率 → 链路。
   因为前三者都是"配置/代码"层面的，成本低、概率高；
   链路问题需要抓包和查交换机，成本最高且最少见。

## 一页速记

```text
四个上限，取最小
  线速 / 固定成本 / 在途深度 / 网卡消息率

固定成本 1500 ns（[假设]，结构稳定）
  填 WQE 350 | doorbell 150 | 取 WQE 250 | 对端写内存 300 | CQE+poll 450
  PCIe 三段合计 700 ns = 47%

有效带宽 = 线上 / (固定 + 线上)
  1 KB @ 100G = 5.2%   1 KB @ 400G = 1.3%   <- 越快越浪费
  1 MB @ 400G = 93.3%
  小消息的消息率与带宽无关：0.63~0.67 M msg/s

消息率提升（1 KB @ 100G，单 QP 0.632M）
  inline          1.19x   （砍 250 ns，大消息无效）
  doorbell batch  1.10x   （最不值）
  CQ moderation   1.36x   （占固定成本 30%）
  三者叠加        2.06x   -> 仍要约 10 个 QP 才打满

延迟拆解（1 KB @ 100G，RTT 2us，合计 2.58 us）
  固定 58%  >  传播 39%  >  线上 3.2%
  -> 降延迟先压固定成本，换网卡排最后（收益 2.4%）

可达带宽 = 在途条数 x 消息大小 / RTT
  400G / 5us / 深度128 / 1KB -> 210G（52%），且无任何错误
  400G / 20us -> 需要约 2000 个在途，必须改架构

深度 = BDP / 消息大小 x 2~4
  BDP = 带宽 x RTT；400G@5us = 244 KB -> 1KB 需 244，x2 = 488

排障顺序：固定成本 -> 在途深度 -> 网卡消息率 -> 链路
```
