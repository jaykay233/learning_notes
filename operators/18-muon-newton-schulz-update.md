### 为什么现在讲这个

这道题表面上「只是一串矩阵乘」，但有三个具体的坑，每一个都会让实现白做：

- **公式有三处只能靠例子判定**。`V` 的组合形式、`ε` 是否在、缩放因子，三者在图片里都缺失。其中 `V` 的组合形式在 `momentum = 0.9` 下的两种写法相差 **10 倍量级**（`G` 的权重是 `1` 还是 `0.1`），猜错则全题皆错，而错误现象和「内核算错」长得一模一样。
- **「5 步迭代」不是「求精确极因子」**。直觉会认为迭代应该收敛到 `σ = 1`，于是看到 `σ_max = 1.20` 就以为有 bug。实测（§2）显示：`p(1) = 0.701`，多项式在 `σ ≈ 0.54` 处有个 `1.2023` 的极大值，所以 `σ_max` **停在那里不动**。这不是没收敛，是设计如此。
- **瓶颈判断容易搞反**。它和 MoE 那道题是镜像：MoE 是「算得少、搬得多、还负载不均」，Muon 是「算得多、搬得少、完全均匀」。同一个 tile 尺寸在两道题里的取舍依据完全不同。

因此本节交付的是一套能**自我验证**的东西：先用 PyTorch 把公式钉死，再用对拍脚本把错误定位到具体行带，最后才谈 GEMM 怎么写快。

## 1. 完整公式

```text
① 混合    V  = momentum·Buf + G             ← 形式待确认（§1.1）
② 归一化  X0 = V / (‖V‖_F + ε)              ← ε = 1e-7
③ 迭代    A  = X Xᵀ
          B  = b·A + c·A²
          X  = a·X + B·X                    重复 5 次
④ 缩放    out = s·X5,  s = sqrt(max(M,N))
```

系数 `a = 3.4445, b = −4.7750, c = 2.0315`。

`M > N` 时在转置上迭代，记 `R = min(M,N)`、`C = max(M,N)`，工作矩阵 `R × C`，Gram 矩阵 `R × R`。这个变换是**精确等价**，不是近似：

```text
在 V 上:   (V Vᵀ)^k · V
在 Vᵀ 上:  (Vᵀ V)^k · Vᵀ   ≡   [ (V Vᵀ)^k · V ]ᵀ
```

它只省 FLOP（Gram 从 `M×M` 降到 `N×N`），不改变结果，只有 float32 的舍入顺序差异。

### 1.1 `ε` 可以反推，`V` 的形式不行

**`ε` 必须存在**：题面有一组「全零输入」用例。若归一化是 `V / ‖V‖_F`，`0/0 = NaN`，整题就没有定义的结果。所以必然是 `V / (‖V‖_F + ε)`。

**`V` 的形式有两个现实依据、且指向不同答案**：

| 候选 | 依据 |
|---|---|
| `momentum·Buf + G` | 题面字面写 "combine the buffer and the gradient" |
| `momentum·Buf + (1−momentum)·G` | 题面声明 "no Nesterov momentum"，而 PyTorch Muon 的非 Nesterov 分支正是 `buf.lerp_(g, 1-momentum)` |

**不能猜。** `M=2, N=3` 的例子足以判定：两种形式给出的 `V` 差 10 倍，输出必然对不上。对拍脚本（§8）把 `V_MODE` 做成一个常量，改一个数字即可切换。

## 2. 心智模型：整个算子 = 奇异值上的一维标量映射

这是本题最重要的一条，它把 `5 × 3 = 15` 个矩阵乘的直觉压缩成一个标量函数。

设 `X = U Σ Vᵀ`（零奇异值不影响结论，因为 `p(0) = 0`）。代入迭代：

```text
A   = X Xᵀ        = U Σ² Uᵀ
B   = b·A + c·A²  = U (bΣ² + cΣ⁴) Uᵀ
B·X               = U (bΣ² + cΣ⁴) Σ Vᵀ
X₁  = a·X + B·X   = U (aΣ + bΣ³ + cΣ⁵) Vᵀ = U p(Σ) Vᵀ
```

**`U` 和 `V` 全程不变，只有 `Σ` 被逐元素施加 `p`。** 所以

```text
out = √max(M,N) · U · p⁵( Σ / ‖Σ‖_F ) · Vᵀ
```

5 步迭代 = 对每个奇异值独立施加 5 次同一个一维多项式。所有数值直觉都可以退化成一维函数 `p` 的性质。

### 2.1 实测轨迹（`1024×1024` 高斯，`momentum = 0.9`）

用配套脚本可复现（`python muon_reference_check.py --trace 1024 1024`）：

| step | `σ_min` | `σ_max` | `σ_max` 距 1 |
|---|---|---|---|
| 0 | 4.82e-05 | 0.0619 | 0.938 |
| 1 | 1.66e-04 | 0.2122 | 0.788 |
| 2 | 5.72e-04 | 0.6860 | 0.314 |
| 3 | 1.97e-03 | **1.2024** | 0.202 |
| 4 | 6.79e-03 | **1.2024** | 0.202 |
| 5 | 2.34e-02 | **1.2023** | 0.202 |

两个必然会被误判成 bug 的现象：

1. **`σ_max` 停在 1.2023 不动。** 它不是「没收敛」，而是撞上了 `p` 的**极大值**：
   ```text
   max_{σ∈[0,1]} p(σ) = 1.2023,  在 σ ≈ 0.54 处取到
   ```
   某个奇异值走到 0.54 附近，下一步被送到 1.2023，然后从这个峰顶再被送下去，形成稳定振荡。
2. **`σ_min` 只有 0.0234**，缩放后是 `0.748`。这正对应题面说的「方阵高斯输入实测低到 0.001–0.02」。矩形输入好得多（见下）。

### 2.2 矩形 vs 方阵，实测差异

| 形状 | 工作矩阵 | 5 步后 `σ/‖σ‖_F` | 缩放后 `σ` | RMS |
|---|---|---|---|---|
| 1024×1024 | 1024×1024 | [0.0234, 1.2023] | [0.748, 38.48] | **0.910** |
| 1024×768 | 768×1024 | [0.682, 1.147] | [21.82, 36.70] | **0.915** |
| 768×1024 | 768×1024 | [0.682, 1.148] | [21.82, 36.73] | **0.914** |

矩形输入的 `σ_min` 是 `0.68` 而不是 `0.023`，因为矩形矩阵没有接近 0 的奇异值需要被抬升。

**顺带一个必须说清的偏差**：题面说「缩放后 RMS = 1」。实测是 **0.910**，因为 `σ_max` 落在 1.20 而非 1。这是「半正交矩阵奇异值全为 1」这个启发式与 5 步近似之间的固有差距。**不要为了让 RMS 归 1 去改缩放因子**，严格按 `√max(M,N)` 乘。

### 2.3 一维映射的解剖

```text
p(σ)   = 3.4445σ − 4.775σ³ + 2.0315σ⁵
p'(σ)  = 3.4445 − 14.325σ² + 10.1575σ⁴

p(0)   = 0          ← 零奇异值永远为 0，迭代不会把秩补上
p(1)   = 0.7010     ← 注意不是 1
p'(0)  = 3.4445     ← 小 σ 被快速抬升，同时放大误差
p'(1)  = −0.7230    ← 1 附近是收缩的
min p' ≈ −1.606     ← 在 σ ≈ 0.84 处，是全局最强放大点
```

不动点解 `p(σ) = σ` 得 `σ ≈ 0.868` 与 `σ ≈ 1.264`（另有 `σ = 0`）。`σ = 0.868` 处 `p' ≈ −1.6`，是**排斥**的，所以轨迹不会停在那里：

```text
从 σ = 1 出发：   1.000 → 0.701 → 1.114 → 0.721 → 1.090 → 0.696 → 1.119
                                                       ↑ 5 步后落在 2-周期附近
从 σ = 1e-3 出发：1.000e-03 → 3.444e-03 → 1.186e-02 → 4.086e-02 → 1.404e-01 → 4.705e-01
```

**「结果依赖步数奇偶」这件事是规格的一部分。** 不要加第 6 步「让它更收敛」——题面明确写了「the 5-step iteration itself defines the expected result」。

## 3. 分类与 roofline

### 分类

| 特征 | 本题 |
|---|---|
| 类别 | contraction / GEMM 型，**复合算子** |
| 内核数 | 每 iter 3 个 GEMM + 2 个 elementwise，共 5 iter |
| 依赖关系 | **严格串行**，零跨 kernel 并行 |
| 不存在的东西 | 分组维、ragged、空段、负载不均、split-K |

这和 MoE 那道题正好互补。那题的全部复杂度在「归约维参差 + 负载倾斜」，这题的全部复杂度在「公式钉死 + GEMM 效率」。

### Roofline（T4：8.14 TFLOPS / 320 GB/s / 40 SM，`I = 25.4 FLOP/B`）

| 项 | 数值 | 推导 |
|---|---|---|
| 每 GEMM | 2.15 GFLOP | `2 × 1024³` |
| 每 iter | 6.44 GFLOP | 3 个 GEMM |
| 总量 | **32.2 GFLOP** | 5 iter |
| 理想访存 | ~180 MB | 15 × 12 MB（每 GEMM 读 2 写 1 个 4 MB 矩阵） |
| `T_c` | **3.96 ms** | `32.2e9 / 8.14e12` |
| `T_m` | 0.56 ms | `180 MB / 320 GB/s` |

**结论：纯计算受限，`T_m` 只有 `T_c` 的 14%，所以这题不像 MoE 那样卡在带宽边缘。** 容错空间大，但也没有「靠 L2 省带宽」的翻盘空间。

再验 tile 是否安全：128×128 时 `1/128 + 1/128 = 0.0156 ≤ 1/(2I) = 0.0197` 过关；64×64 是 `0.03125` 超阈值 → 算术强度掉到 `16 FLOP/B < 25.4`，直接变带宽受限。**所以 128×128 是这道题的下限，不是偏好。**

（T4 没有 TF32、且题目禁止半精度操作数，FP32 SIMT 的 8.14 TFLOPS 就是硬顶，没有张量核捷径。）

## 4. 下标三分法：这一节几乎自动通过

以第一个 GEMM 为例：

```text
A[i][j] = Σ_k X[i][k] · X[j][k]
  ↑  ↑       ↑
  |  |       └─ 归约维 k，长度固定 1024，无 ragged、无空段
  └──┴─ 独立维 i, j
```

**没有分组维。** 所以前两节的所有机制（`group_offsets` 间接寻址、空组写零、按段长排序、选择性 split-K）在这里**全部不适用**。

归约维层级：`k = 1024`，线程内串行，不 split。判据仍是那一条 —— 跨 block 归约的成本正比于输出大小（4 MB/GEMM），收益只是一段 1024 长的串行累加，不划算。

## 5. 波的正确模型（含一次需要撤回的更正）

这一节记录我在同一道题上**改口两次**的过程，因为「波」这个词很容易用错。

### 5.1 正确的 makespan 模型

关键是：**`__launch_bounds__(256, 2)` 里的 `2` 是「驻留数」，用于藏延迟，不是「吞吐翻倍」。** 两个 co-resident block 共享同一个 SM 的 FMA 单元，总吞吐不变。所以

```text
makespan ≈ ceil(nblocks / nSM) × T_block
T_block  = (单个 tile 的 FLOP) / (单 SM 峰值)
利用率   = nblocks / (nSM × ceil(nblocks / nSM))
```

**量化的单位是 SM 数（40），不是槽位数（80）。**

### 5.2 用 1024×1024 验证

`T_block = 2×128×128×1024 / 203.5e9 = 165 µs`。

| 方案 | nblocks | `ceil(n/40)` | makespan | 利用率 |
|---|---|---|---|---|
| 完整 GEMM | 64 | 2 | **330 µs** | 64/80 = 80% |
| SYRK（上三角 36 块） | 36 | 1 | **165 µs** | 36/40 = 90% |

### 5.3 我的两次改口

| 版本 | 说法 | 判定 |
|---|---|---|
| v1 | 「SYRK 省 33% FLOP → 3.96 变 2.64 ms」 | 方向对，但把原因全归给 FLOP |
| v2 | 「SYRK 在 1024² 上没用，因为 64 和 36 个 block 都装进一波，单 block 工作量不变」 | **错**。错在假设两种情况 makespan 都等于 `T_block`。64 个 block 落在 40 SM 上，必有 SM 分到 2 块 → makespan 是 `2·T_block` |
| v3 | `ceil(nblocks/nSM)` 量化 → SYRK 让那两个 GEMM 的轮数从 2 降到 1 | 采用 |

**结论：SYRK 确实有 ~33% 收益，v2 的「没用」是错的。** 方法论教训：**当「减少 FLOP」和「减少轮数」同时发生时，两者会叠加，不能靠「都在一波里」把它抹掉。**

### 5.4 顺带纠正一张旧表

用 `ceil(n/40)` 重算 tile 尺寸与利用率：

| tile | nblocks | `ceil(n/40)` | 利用率 | 算术强度 | 可用? |
|---|---|---|---|---|---|
| 256×128 | 32 | 1 | 80% | 51 FLOP/B | 寄存器装不下 |
| **128×128** | 64 | 2 | **80%** | **32 FLOP/B** | ✓ |
| 128×64 | 128 | 4 | 80% | 21 FLOP/B | ✗ 变带宽受限 |
| 64×64 | 256 | 7 | 91% | 16 FLOP/B | ✗ 变带宽受限 |
| 32×32 | 1024 | 26 | 98.5% | 8.5 FLOP/B | ✗ 严重带宽受限 |

所以「80% 是硬天花板」这个说法是错的：小 tile 能到 91% / 98.5%，但算术强度掉到阈值以下。**128×128 胜出的真正理由是算得上、且不算带宽账，而不是利用率。** 附带一个否定结论：`128×64` 的利用率和 `128×128` 一样是 80%，所以「减小 tile 以提高利用率」这条建议本身也错，还额外多一倍重复读。

## 6. SYRK：对称性能省多少

```text
A = X Xᵀ   ⇒  A 对称        （严格对称：是我们自己镜像写出的同一块内存）
A² = A A   ⇒  A² 也对称
```

所以 `XXᵀ` 和 `A@A` 都是 SYRK，只需算上三角：

| GEMM | 完整 FLOP | SYRK FLOP | 轮数（1024²） |
|---|---|---|---|
| `A = X Xᵀ` | `2R²C` = 2.15 G | `R²C` = 1.07 G | 36 块 → 1 轮 |
| `A² = A A` | `2R³` = 2.15 G | `R³` = 1.07 G | 36 块 → 1 轮 |
| `B @ X` | `2R²C` = 2.15 G | 不减（不对称） | 64 块 → 2 轮 |
| **每 iter** | 6.44 G | 4.30 G | 660 µs |
| **5 iter** | 32.2 G | 21.5 G | **3.30 ms** |

对比不做 SYRK 的 `5 × 3 × 330 µs = 4.95 ms`：**−33%**，从 4.95 ms 掉到 3.30 ms。

实现要点：

- 只对 `tileI ≤ tileJ` 的 tile 发 block，算完镜像写入另一半。
- 对角 tile 内部也对称，可再省一半，但只占 8/36，收益小，先不做。
- 镜像写代价：每 GEMM 多 4 MB 读 + 4 MB 写 ≈ 0.025 ms，10 个 SYRK GEMM 共 0.25 ms。相对省下的 1.65 ms 完全值得。
- 对角线的 tile 若也算半份（`i ≤ j` 的内部三角），需要 tile 内掩码，复杂度上升，先不做。

## 7. 实现骨架：三个 GEMM 用两个 kernel

完整代码：[code/muon/muon.cu](code/muon/muon.cu)（已与 PyTorch float64 规格参考对拍通过）。

| 调用 | 形态 | `TRANS_B` | 归约长度 |
|---|---|---|---|
| `X Xᵀ` | NT | `true`（两个操作数是同一指针） | `C` |
| `A @ A` | NT —— 因 `A` 对称，`A A ≡ NT(A,A)` | `true` | `R` |
| `B @ X` | NN + 融合 epilogue | `false` | `R` |

`A @ A` 走 NT 是个便宜：对称性让「NN 的 B 按列取」退化成「按行取」，省掉一整套转置 load。

其余参数与 17 号笔记的 MoE 案例**同构**（都是 128×128 tile 的 FP32 GEMM）：

```text
tile 128×128, 256 线程 (16×16), micro 8×8 = 64 累加器
BK = 8, 双缓冲 smem = 2×(128×8 + 8×128)×4B = 16896 B
__launch_bounds__(256, 2) → 128 reg/thread
每 stage 一次 __syncthreads()（cur 在算、nxt 在写，两个 buffer 不冲突）
```

三个可以省掉的往返：

1. **`X ← aX + B@X` 融进 epilogue**：线程手里已有 `acc`，直接写 `alpha·Xold + acc`，省一个 4 MB 读 + 4 MB 写，5 次迭代省 40 MB。
2. **`Bm` 复用 `A²` 的缓冲**：先 `Bm = A@A`，再原地 `Bm = c·Bm + b·Am`。同一元素由同一线程先读后写，安全。
3. **workspace 静态缓存**：`cudaMalloc` 每次调用会引入 0.1–1 ms 噪声，而 benchmark 会反复调 `solve`。总量 16 MB（`X`、`X2` 各 `R×C`，`Am`、`Bm` 各 `R×R`）。

### 7.1 `M > N` 的转置写回是独立的一类坑

`output` 是 `M×N`，但结果在 `N×M` 的缓冲里。直接 `out[i][j] = buf[j][i]` 会让 warp 内地址跨行，**32 倍减速**。必须用 32×32 的 smem 分块转置。

而它的一个具体失败模式值得单独记：**如果 kernel 内部认为 `blockIdx.x` 对应 M、而 grid 按 N 来开，就会只覆盖一部分行，剩余的整片保持未初始化。** 表现是「头部数值全对、尾部成片为 0」，`max abs diff` 看起来只是从 4.85 降到 4.00，很难看出根因。

**根治办法：不要用二维 grid。** 用一维 `blockIdx.x` 自己解码：

```cuda
const int nTilesN = (N + 31) >> 5;
const int bi = (blockIdx.x / nTilesN) * 32;   // M 方向
const int bj = (blockIdx.x % nTilesN) * 32;   // N 方向
```

一旦只有一个 block 维度，就没有「`x` 是哪个维度」可以搞反。这个改动看起来笨，但它把一个**已经犯过两次**的错误变成了不可表达。

## 8. 对拍方法：分三层，越往下越省时间

这道题有**三个不同的「参考」**，定义不同，按设计就不相等。混在一起对拍会得到错误结论：

| 参考 | 内容 | 与本题规格的关系 |
|---|---|---|
| **R1 规格** | 5 步 NS + 系数 + `ε` + `√max(M,N)` | **就是判题标准** |
| PyTorch Muon | 同一迭代，缩放用 `0.2·√max` | 差**恒定 5 倍** |
| 精确极因子 | `U Vᵀ` | 差 1e-2 量级（方阵高斯本征） |

**判对错只看 R1。** 配套脚本 [code/muon/muon_reference_check.py](code/muon/muon_reference_check.py) 只对齐 R1，故意不引入另外两个。

### 四组测试

| 组 | 比什么 | 能定位什么 |
|---|---|---|
| 1 | float32 仿真 vs float64 参考 | 公式理解正确性（不需要 GPU） |
| 2 | `Buf=0, momentum=0`（则 `V = G`） | **把 NS 迭代与 V 组合/转置的嫌疑分开** |
| 3 | 边界：全零、`G` 全零、`1e-8`、单元素 | `ε` 是否生效、有没有 NaN |
| 4 | CUDA 内核 vs float64，再 vs float32 仿真 | 内核实现是否正确 |

第 4 组的两级比对是核心：**CUDA vs float32 仿真应该只剩舍入（相对 1e-5）。** 若这一级就超差，问题一定在 kernel；若这一级干净但 CUDA vs float64 超差，问题在公式理解或 float32 累积误差。

### 诊断输出比 `max abs diff` 有用得多

`report()` 有两个探针：

```text
⚠ 196608 个元素 want 非零而 got 为 0
  首个位置 (row, col) = (768, 0)
  涉及行 768 … 1023（256 行，占 25.0%）

  超出容差的行带 4/16:
    行 [  768,   832)  max_diff=4.03e+00  ← 整带为 0
```

`max abs diff = 4.00` 不告诉你坏在哪，而上面两段直接说出「768～1023 行没写」。**只看标量误差，是这次多花两轮的直接原因。**

## 9. 数值敏感性：能不能靠「换个 tiling」过容差

由 §2，误差分析完全退化成一维：`p` 的导数就是误差放大系数。

```text
|p'| 在 σ ∈ [0.5, 1.2] 上最大 1.6
5 步 = 4 次映射 → 放大 ≤ 1.6⁴ ≈ 6.6 倍
只有 σ → 0 时才有 3.44⁴ ≈ 140 倍放大，但那里 σ 本身可忽略
```

**合起来最坏约 10 倍。** FP32 GEMM 的相对舍入约 `1e-7`，放大后约 `1e-6`，远在 `1e-4` 级容差内。

实测印证（`--lib` 未提供时，float32 仿真 vs float64 参考）：

| 形状 | max abs diff |
|---|---|
| 1024×1024 | 2.41e-05 |
| 1024×768 | 3.00e-05 |
| 768×1024 | 2.31e-05 |
| 37×91 | 5.01e-06 |

**实践含义**：不同的 tiling / 累加顺序不会导致不通过，可以放心优化 GEMM。但反过来说，**不要「改进」迭代的形式** —— 把 `B = bA + cA²; X = aX + B@X` 改写成代数等价的 `X = aX + b(AX) + cA(AX)` 虽然数学相同，舍入路径不同。题面已声明「迭代本身定义期望结果」，照参考实现的顺序写最稳。

## 10. 边界用例

| 用例 | 会发生什么 | 处理 |
|---|---|---|
| **全零 `G, Buf`** | `‖V‖_F = 0`，无 `ε` 则 `0/0 = NaN` | `ε = 1e-7` 后 `inv = 1e7`，但 `X` 全零，乘完仍 0 → 输出全 0 ✓ |
| **`G` 全零、`Buf` 非零** | `V = momentum·Buf`，正常路径 | 无特殊处理 |
| **`1e-8` 量级** | 归一化被 `ε` 稀释 | 见下 |
| **`M=1` 或 `N=1`** | `R = 1`，Gram 是 1×1 | 同一 kernel 能跑，极端低效但正确 |

### `1e-8` 用例里 `ε` 稀释多少？——要按规模算

`ε` 的相对影响是 `ε / (‖V‖_F + ε)`，而 `‖V‖_F ≈ sqrt(MN) × 1e-8`：

| 形状 | `‖V‖_F` | `ε` 占比 |
|---|---|---|
| 64 × 48（实测） | 7.55e-07 | **11.7%** |
| 1024 × 1024 | 1.0e-05 | ~1% |

**同一组 `1e-8` 输入，矩阵越大 `ε` 稀释越少。** 这类用例的偏差在 1%～12% 量级，属规格行为，不是 bug —— 不要试图「修正」它，因为判题用的参考实现带同一个 `ε`。

## 11. 自检

**Q1.** 迭代 5 步后 `σ_max = 1.2023` 而不是 1，怎么判断这是 bug 还是规格？

<details><summary>答案</summary>

算 `p` 在 `[0,1]` 上的极大值：`max p(σ) = 1.2023`，在 `σ ≈ 0.54` 处取到。因为 `p(1) = 0.701 < 1.2023`，任何走到 0.54 附近的奇异值下一步必然被送到 1.2023。
更快的判定：跑 `--trace`，看 `σ_max` 是不是**稳定**在某个值。稳定而非持续增长/发散，就说明它撞上了多项式的峰，属规格。

</details>

**Q2.** 为什么 `A @ A` 可以用 NT 形态算，而 `B @ X` 不行？

<details><summary>答案</summary>

`A = X Xᵀ` 精确对称（`A[i][j]` 与 `A[j][i]` 是同一块内存），所以 `A A` 等价于 `A Aᵀ`，即 NT。
`B` 也对称，但 `B @ X` 的第二个操作数是 `X` 而不是 `B`，整个乘积不对称，只能按 NN 算（或对 `X` 做转置 load）。
这个等价依赖「精确对称」而非「近似对称」—— 前提是自己的镜像写保证位级相同。

</details>

**Q3.** 64 个 block 落在 40 个 SM 上，利用率多少？改成 36 个呢？为什么不能用「都装进一波」解释？

<details><summary>答案</summary>

`ceil(64/40) = 2` 轮 → `64/80 = 80%`。36 个 block：`ceil(36/40) = 1` 轮 → `36/40 = 90%`。
不能用「都装进一波」解释，因为一波能装 80 个（2 block/SM 驻留），这只影响**并发数**不影响**吞吐**：两个 co-resident block 共享同一 SM 的 FMA 单元，2 块就要跑 2 倍的 `T_block`。量化单位是 SM 数，不是槽位数。
这正是「SYRK 省 33%」能兑现的原因：它把两个 GEMM 的轮数从 2 降到 1。

</details>

**Q4.** 对拍时 CUDA vs float32 仿真的差异是 3e-4，而 float32 仿真 vs float64 只有 2e-5。问题在哪？

<details><summary>答案</summary>

第一级干净，说明公式理解对、float32 累积误差只有 2e-5。
第二级超差 10 倍以上，说明**内核实现**与预期不一致 —— 常见原因按顺序：`G`/`Buf` 被原地改过（必须只读）、归一化用了 `X@X` 的迹而不是 Frobenius 范数、`b` 与 `c` 在 `axpby` 里位置互换、转置写回漏行。
先跑第 2 组（`momentum=0, Buf=0`）把范围再缩小一半。

</details>

**Q5.** 为什么 `1e-8` 用例的偏差不能靠「提高归一化精度」清掉？

<details><summary>答案</summary>

偏差不来自精度，来自 `ε` 本身：`V/(‖V‖_F + ε)` 与 `V/‖V‖_F` 的相对差就是 `ε/(‖V‖_F+ε)`，64×48 时是 11.7%。
这是**规格定义的**归一化，判题参考实现带同一个 `ε`，所以正确做法是照抄，不是「修好」。

</details>
