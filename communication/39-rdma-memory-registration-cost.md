## 为什么现在讲这个

[33 章](./33-rdma-six-layer-spine.md) 对 Q19 只有一句话：FRWR 把注册拆成"钥匙 + 绑定地址"，
MW 在不重新注册的前提下临时授权子区间，**动机都是让"地址变化"变便宜**。

这句话是对的，但它躲开了所有难的问题：

> 为什么"变便宜"值得专门发明两个机制？
> 便宜多少？按什么计费？
> 什么情况下 FRWR 反而更贵？

[38 章](./38-verbs-program-walkthrough.md) 里 `ibv_reg_mr` 只调用了一次——那是服务端常驻程序的写法。
一旦进入存储路径，缓冲每笔 IO 都在变，注册就从"一次开销"变成"每笔开销"。
**这才是 FRWR 存在的真正场景。**

这一章要把这件事算清楚，并且给出一个反直觉的结论：**在小 IO 上，FRWR 比 reg_mr 更贵。**

---

## 心智模型：注册成本按页收费，所以它有两种税

`ibv_reg_mr` 做的事（[33 章](./33-rdma-six-layer-spine.md) 推论 2）：pin 页 → 建 MTT 表项 → 生成
lkey/rkey。其中**建表是逐页的**，这是全部的关键：

```text
注册成本 ≈ 固定开销 + 页数 × 每页成本
页数     = IO 大小 / 页大小（4 KB）
```

于是"每笔 IO 都注册一次"有两种完全不同的读法：

| 口径 | 公式 | 结论 |
| --- | --- | --- |
| 带宽税 | 注册成本 / 线上时间 | 页成本和线上时间都随大小线性涨 → **比值固定 ≈ 30%** |
| 延迟税 | 注册成本 / 端到端延迟 | 小 IO 时线上时间本来就短 → 占比看起来很大，但绝对值小 |

**必须先用对口径。** 用带宽口径看 4 KB IO 会得出"92% 的税"这种吓人数字，
但它实际的延迟只涨 16%。

### 逐页成本的固定比值是怎么来的

```text
每页注册成本  = 100 ns                                    [假设]
每页线上时间  = 4096 B / 12.5 B/ns = 327.7 ns            (100 Gbps)
比值          = 100 / 327.7 = 30.5%
```

两者都正比于页数，所以**比值与 IO 大小无关**。这就是"存储节点跑不满线速"的结构性原因：
不是网卡不行，是每笔 IO 都在重建翻译表。换更快的网卡不会让这个比例变好，
因为线上时间也同比缩小——**比值只由"每页成本 / 每页线上时间"决定**，也就是由
`100 ns` 和链路速率决定。链路越快，这个税越重。

## 完整计算

脚本 [`39_memory_registration_cost.py`](./39_memory_registration_cost.py) 的核心只有三行：

```python
def link_ns(size_b):
    return size_b / BYTES_PER_NS               # 12.5 B/ns @ 100Gbps

def reg_cost(size_b):
    pages = max(1, -(-size_b // PAGE_B))       # 向上取整
    return REG_FIXED_NS + pages * COST_PER_PAGE_NS

# FRWR / MW 的成本与大小无关，只按"笔"收费
```

跑起来：

```bash
cd ~/Downloads/learning_notes
python3 communication/39_memory_registration_cost.py
```

第一张表（单位 ns）：

```text
     IO 大小     页数      线上 ns   reg_mr ns     带宽税   FRWR ns     带宽税    MW ns
      4 KB      1      327.7       300.0    92%     500.0   153%    300.0
     64 KB     16     5242.9      1800.0    34%     500.0    10%    300.0
    256 KB     64    20971.5      6600.0    31%     500.0     2%    300.0
    512 KB    128    41943.0     13000.0    31%     500.0     1%    300.0
   1024 KB    256    83886.1     25800.0    31%     500.0     1%    300.0
   4096 KB   1024   335544.3    102600.0    31%     500.0     0%    300.0
```

**64 KB 往上，reg_mr 的带宽税稳定在 31%**，不再变化。这就是那条"恒定比例"的直观形态。

第三张表（交叉点）：

```text
   pages = (500 - 200) / 100 = 3.0
   -> IO 小于 12 KB 时，reg_mr 的单次成本低于 FRWR
```

第二张表（延迟口径）：

```text
     IO 大小      基线 ns      reg_mr      增加        FRWR      增加
       4 KB       1828        2128    16%        2328    27%
      16 KB       2811        3411    21%        3311    18%
      64 KB       6743        8543    27%        7243     7%
```

**4 KB 时 FRWR 比 reg_mr 慢**：一次 fast_reg WR（500 ns）比注册一页（300 ns）还贵。
这不是模型假象——真实实现里 FRWR 的收益来自"避免 pin 页 + 避免内核路径"，
在单页场景下这些收益抵不过一次额外的 WR 往返。

## 第四张表：每笔都 reg_mr 时的带宽上限

```text
     IO 大小     理想 Gbps     实际 Gbps      损失
       4 KB       100.0        52.2    48%
      64 KB       100.0        74.4    26%
     512 KB       100.0        76.3    24%
    1024 KB       100.0        76.5    24%
    4096 KB       100.0        76.6    23%
```

**封顶在 76 Gbps 左右**，不再随 IO 变大而改善。这就是那个 30% 的税在带宽上的样子。

对照 [33 章](./33-rdma-six-layer-spine.md) 第四段：`ib_write_bw` 跑不满时，
先把消息调大是个本能反应。但如果你的实现每笔都 `reg_mr`，**把 IO 从 4 KB 调到 4 MB
只能把带宽从 52 Gbps 提到 76 Gbps**，剩下的 24% 是结构性的，调参调不出来。

## FRWR 的真实约束：key 池深度

FRWR 把钱变成了 O(1)，代价是**每笔在途 IO 要占一个 key**，而且用完了必须
`IBV_WR_LOCAL_INV` 才能复用。于是：

```text
打满带宽需要的在途 IO 数 ≈ (线上时间 + RTT) / 单 IO 线上时间
```

脚本第五张表：

```text
     IO 大小      线上 ns       打满需在途     需要 key 数
       4 KB      327.7        16.3           17
      64 KB     5242.9         2.0            2
     512 KB    41943.0         1.1            2
```

**4 KB 随机 IO 需要 17 个 key 才能打满带宽，512 KB 只要 1 个。**

这条结论有直接的操作含义：如果你的 NVMe-oF target 配了 8 个 key 池，
跑 4 KB 随机读时带宽上限大约是理想的 8/17 ≈ 47%——**队列深度看起来够，
但 key 不够**，而监控上你不会看到任何"资源不足"的告警，只看到带宽上不去。

## 一次 NVMe-oF 读 IO 里，两端各付什么

```text
主机（initiator）
  1. 选一个空闲 key（FRWR MR）
  2. post_send: IBV_WR_RDMA_READ，目标 = 对端 buffer + rkey
  3. 数据直接落进主机用户缓冲（不经内核拷贝）
  4. post_send: IBV_WR_LOCAL_INV，把 key 失效以便复用
  5. CQE 到达 -> 这笔 IO 完成

目标（target）
  1. 收到 READ 请求
  2. 从设备/page cache 取数据到 buffer
  3. 该 buffer 必须已注册，或临时 fast_reg
  4. NIC 从 buffer DMA 出去
```

注意主机侧第 4 步的**时机**：`LOCAL_INV` 必须在这笔 IO 的 CQE 之后。
提前失效会让 key 被下一笔 IO 复用，而上一笔的 READ 可能还在飞——结果是把新 IO 的数据
覆盖掉旧 IO 的缓冲，表现为"偶发数据错乱，压力越大越容易复现"。

目标侧的顺序约束更危险：**必须先 `fast_reg` 再让对端 READ，读完必须 `local_inv`**。
漏掉 `local_inv` 的后果不是报错，而是对端可以继续读一段已经释放或重新分配的内存——
这是一个**安全边界问题**，不只是性能问题（对应 [32 章 Q54](./32-rdma-interview-questions.md)）。

## MW 和 FRWR 的区别：共享注册 + 子区间授权

MW 的动机和 FRWR 一样（让地址变化变便宜），但机制不同：

| | FRWR | MW |
| --- | --- | --- |
| 注册什么 | 一个"钥匙" MR，绑定到新地址 | 一块已注册**大 MR** 的子区间 |
| 谁发起 | 本地 `fast_reg` WR | 本地 `bind_mw` WR |
| 主要用途 | 内核态存储 IO（NFS/RDMA、NVMe-oF） | 用户态，动态授权远端访问 |
| 关键约束 | key 池深度 | 子区间必须在大 MR 范围内、权限不超母区间 |
| 是否 pin 新页 | 是（但走快路径） | **否**（母 MR 已 pin 完） |

MW 的核心优势是**完全不用 pin 新页**：母 MR 在启动时注册一次，之后只在它的范围内
做地址/长度的授权。所以对"固定 arena + 动态切片"的结构（[32 章 Q49](./32-rdma-interview-questions.md)
的 KV 设计就是这个形状），MW 比 FRWR 更合适。

## 常见错法，以及症状

| 错法 | 症状 |
| --- | --- |
| 每笔 IO 都 `reg_mr` | 带宽封顶在理想的 ~76%，换网卡无效 |
| 用带宽口径评价小 IO | 误判"92% 的税"，其实延迟只涨 16% |
| key 池只按并发数配 | 4 KB 随机 IO 上带宽只有理想的一半，无任何告警 |
| 忘了 `LOCAL_INV` | key 池逐渐耗尽，新 IO 全 `ENOMEM`，吞吐随时间线性下降 |
| CQE 前就 `LOCAL_INV` | 偶发数据错乱，压力越大越易复现 |
| target 侧漏 `local_inv` | 对端能读已释放内存（安全问题，不是性能问题） |
| MW 的权限超出母 MR | `bind_mw` 直接失败，或远端 `REM_ACCESS_ERR` |
| 先绑地址后写数据 | 对端读到旧数据 |

"忘了 `LOCAL_INV`"这条值得记住它的形状：**吞吐随时间线性下降，重启恢复到满值**。
这种"随时间劣化、重启就好"的曲线，几乎总是资源泄漏（key、slot、credit），
不是网络问题。

## 模型边界

- **每页 100 ns 是量级**：真实值取决于是否命中 page cache、大页、IOMMU、内核版本
- **没有建模内核锁争用**：高并发下 `reg_mr` 的排队成本可能远超逐页成本
- **没有建模 FRWR 的页列表长度限制**：`max_fast_reg_page_list_len` 会强制拆成多个 WR
- **没有建模大页**：用 2 MB 页时页数少 512 倍，"带宽税"几乎消失——这是一个真实可用的优化
- **没有建模 IOMMU**：开 IOMMU 后 pin/映射成本更高，税更重

所以这张表只能判断"量级和方向"，不能作为容量规划依据。真实数字必须实测，
而且要在目标内核版本 + 是否大页 + 是否开 IOMMU 的条件下测。

1. 为什么每笔 IO 都 `reg_mr` 会形成"恒定比例"的带宽税？这个比例由什么决定？
2. 4 KB IO 上 FRWR 为什么可能比 `reg_mr` 更慢？
3. 每笔都 `reg_mr` 时，把 IO 从 4 KB 调到 4 MB 能把带宽从多少提到多少？还差多少？
4. FRWR 的 key 池深度怎么定？4 KB 随机 IO 和 512 KB 顺序 IO 差多少？
5. 忘了 `LOCAL_INV` 和过早 `LOCAL_INV` 分别长什么样？
6. MW 相对 FRWR 的核心优势是什么？什么结构最适合用 MW？
7. 用 2 MB 大页会给"带宽税"带来什么变化？

<details>
<summary>答案</summary>

1. 因为注册成本按页收费，而线上时间也正比于页数，两者都线性 →
   比值固定。比例 = 每页成本 / 每页线上时间 = 100 ns / 327.7 ns ≈ 30.5%（100 Gbps 下）。
   **链路越快，这个税越重**，因为每页线上时间变小。
2. 4 KB 只有 1 页，`reg_mr` 成本约 300 ns；而 FRWR 要额外一次 fast_reg WR（约 500 ns）。
   在单页场景下，FRWR 省下的 pin 页收益抵不过这一次额外 WR 的成本。
   交叉点在约 12 KB（3 页）。
3. 从 52 Gbps 提到 76 Gbps 左右。**剩下 24% 是结构性的**，调大 IO 无法消除，
   因为税是按比例收的。
4. 需要 `(线上时间 + RTT) / 单 IO 线上时间` 个在途。4 KB 需要约 17 个，
   512 KB 只需 1~2 个。所以小 IO 的 key 池深度是吞吐瓶颈。
5. 忘了 `LOCAL_INV`：key 池线性耗尽，新 IO 报 `ENOMEM`，吞吐随时间下降、重启恢复。
   过早 `LOCAL_INV`：key 被下一笔复用，上一笔在途 IO 的数据被覆盖，表现为
   偶发数据错乱，压力越大越明显。
6. **完全不用 pin 新页**（母 MR 启动时已注册），只在已注册大 MR 范围内做子区间授权。
   最适合"固定 arena + 动态切片"的结构，比如 KV 的 slot 池。
7. 页数减少约 512 倍（4 KB → 2 MB），逐页成本几乎消失，"带宽税"基本归零。
   这是真实可用且收益很大的优化，前提是应用能用上大页。

## 一页速记

```text
注册成本的两段:
  固定开销 + 页数 x 每页成本        ← 逐页成本是全部关键

两种口径（必须先选对）:
  带宽税 = 注册成本 / 线上时间     -> 大 IO 稳定在 ~30%（按页收费的必然结果）
  延迟税 = 注册成本 / 端到端延迟   -> 小 IO 看这个，4 KB 只涨 16%

为什么是 30%:
  每页成本 100 ns / 每页线上时间 327.7 ns = 30.5%（100 Gbps）
  链路越快，税越重

每笔 reg_mr 的带宽上限:
  4 KB -> 52 Gbps，4 MB -> 76 Gbps，封顶 ~76（24% 损失，调参调不出来）

FRWR:
  O(1) 成本（一次 fast_reg WR + 一次 local_inv）
  交叉点 ~12 KB：比它还小的 IO，reg_mr 反而更便宜
  key 池深度 = 在途 IO 数：4 KB 需 17 个，512 KB 只需 2 个

MW:
  不动 pin，只在已注册大 MR 内授权子区间
  适合固定 arena + 动态切片（KV slot 池）

三条必查顺序:
  LOCAL_INV 必须在这笔 IO 的 CQE 之后
  target 侧必须先 fast_reg 再放行 READ，读完必须 local_inv（安全边界）
  key 耗尽的表现：吞吐随时间线性下降，重启恢复
```
